# ADR 0027 — Завершение неопределённого приёма Mini App

Дата: 9 сентября 2026 года. Решение принято владельцем для реализации в C6 в полном промпте финальной сессии. Реализация: кандидат; производственная активация и пользовательская приёмка ещё не выполнены.

## Причина и граница изменения

В рабочем Mini App осталась заявка `pending` без принятой задачи. Проверка, отмена и восстановление сессии не завершали её. Произвольное исключение до durable admission воспроизводит этот класс дефекта; первоначальная причина конкретного запроса не сохранена и неизвестна.

Это решение заменяет в [ADR 0025](0025-miniapp-session-and-request-recovery.md) только правило неизменности существующего `pending` при отмене и отсутствие срока его согласования. Авторизация, tenant/owner binding, исходная задача, запрет повторного semantic execution и все принятые границы C0–C5 сохраняются. Восемь критериев C6 не расширяются.

## Принятый механизм

Журнал заявки, её отмена и `ingress_claims` используют одну SQLite write-транзакцию. Новый claim сначала возвращает ранее принятую задачу, если она есть; иначе проверяет защищённую запись Mini App. Отменённая, завершённая непринятой, legacy pending без срока или просроченная заявка не получает нового claim. Это правило действует и для сохранённого черновика очереди при перезапуске. Закрытый черновик завершается штатным подтверждением обработки очереди без исполнения и доставки; история заявки остаётся в журнале.

Новая заявка получает отдельное достоверное время поступления, время изменения и фиксированный срок приёма 90 секунд. Проверка состояния атомарно завершает истёкшее ожидание, если принятой задачи нет. Подтверждённая отмена может сделать это раньше. Если claim победил в гонке, возвращается исходная задача, а её журнал и доставка сохраняются. Сетевой таймаут страницы не является отказом: клиент проверяет исходный request key, не повторяя POST. Прерывание серверного обработчика закрывает только ещё не принятую заявку через ту же транзакцию.

Типизированный semantic failure сохраняет безопасный код и завершает непринятый запрос. Произвольное исключение остаётся неопределённым исходом до атомарной сверки/отмены/срока. Поздний результат разбора не открывает закрытую заявку. Новая попытка владельца после подтверждённого завершения получает новый key.

Первый сохранённый envelope остаётся неизменным на повторах, включая received_at и revision. Для нового envelope received_at берётся при поступлении запроса, а не при выдаче сессии. У старых записей точное время поступления неизвестно: оно не вычисляется из session time. Legacy pending на исправленном единственном Core разрешается тем же путём сверки; ручной SQL и очистка browser storage для ремонта не применяются.

## Диагностика и интерфейс

В существующей DPAPI-защищённой записи сохраняются только envelope с digest содержимого, срок, стадия, типизированный код, стадия отказа и времена. Длительность и короткий отпечаток выводятся из этих данных. Исходный код отказа сохраняется при последующем завершении. Текст запроса, credentials, provider details и полные исключения не добавляются в диагностику.

`/status` отдельно показывает доступность Core, состояние смыслового приёма, исполнителя/голоса, незавершённый приём Mini App и историю задач, требующих внимания. Последний transient semantic failure не является командой перезапуска. После старта смысловой путь честно обозначается как ещё не проверенный, до фактического разбора запроса.

Mini App автоматически делает не более 30 проверок исходной заявки с интервалом 3 секунды; затем оставляет ручную проверку и отмену. Только подтверждённое завершение разблокирует новую задачу. Принятый результат открывает исходную карточку. Содержимое API выводится как текст; секреты и инструкции не сохраняются в browser storage.

## Совместимость и переключение

SQL DDL не меняется. Новые необязательные поля защищённого JSON читают прежние записи без массового переписывания. Старый reader с запретом неизвестных полей не совместим с новыми записями: после начала работы кандидата возврат к прежнему коду над этими БД запрещён. При проблеме — безопасная остановка с сохранением данных и согласованное исправление; автоматического восстановления старой БД поверх production нет.

Перед переключением нужны свежая проверенная копия, точные code/static/config/runtime-input bindings, один остановленный старый Core и отдельное разрешение изменённого плана. После смены кода создаётся новая authenticated копия под его application binding, затем выполняются восстановление в изолированном каталоге, проверка реальных сценариев и остальные исходные условия C6.

## Проверка

Регрессии проверяют неизвестный и известный отказ, отмену во время semantic, accepted-first race, общий claim между соединениями, позднее восстановление очереди, transport cancellation, reload/recovery, неизменность envelope, tenant/auth isolation, честный status и потерянный ACK. Изменённое ожидание прежнего теста отмены подкреплено прямым отказом общего durable claim; прежний тест запрета повторного компилятора для UNKNOWN сохраняется.

Две реальные защищённые записи журнала без текста и уточнений проверены в отдельной пустой fixture: pending завершается, прежний отказ и оба envelopes сохраняются, SQL/content validation проходят. Live БД, бизнес-заметки, задачи и доставки в fixture не копировались; исходные строки live остались неизменными.
