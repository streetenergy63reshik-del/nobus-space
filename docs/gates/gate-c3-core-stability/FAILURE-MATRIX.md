# Gate C3 — отрицательные сценарии и восстановление

**DRAFT / WIP mapping.** Это карта исполняемых проверок, не итоговый PASS.
`MAPPED` означает, что указанный тест существует и его assertions относятся
к сценарию. Результаты запусков и окончательная SHA/tree привязываются отдельно
в EVIDENCE.json после freeze. `MISSING` сохраняет недоказанную часть, даже если
рядом есть полезные частичные проверки. Старые C0–C2 не принимаются повторно.

База: `5fdc28ce66dbb072acd6676baf72fe58ae10b4b3`, tree
`c8e756fb00874c5db2f6105c6d65154d0ed243e7`.
Границы — [WORKING-CONTRACT](WORKING-CONTRACT.md) и [ADR 0024](../../adr/0024-core-durable-recovery-and-part-delivery.md).
Все payload синтетические, SQLite disposable; реальные внешние эффекты,
Telegram send и provider/ASR calls эти проверки не выполняют.

Во всех строках запрещены второй logical task/result, чужие tenant/task refs,
успех без authoritative evidence и раскрытие private payload/служебных путей.
Видимые состояния используют существующий `ProductTaskStatus`: «В очереди»,
«В работе», «Ожидает действия», «Готово», «Требует внимания», «Не выполнено».
«Готово» для проверенного результата само по себе не означает подтверждённую
доставку; delivery pending/unknown отражается отдельно.

## Границы карты

Все 34 сценария сопоставлены с исполняемыми проверками в указанном выше объёме.
Они остаются MAPPED до полного C3 L1 и независимого review окончательных bytes;
карта сама по себе не разрешает объявить реализацию принятой или закрыть issue.

Hard process exit называется так только для теста с реальным `os._exit`.
Exception injection, reopen Python objects и fault-controlled clocks не
называются hard crash. Synthetic Telegram transport не доказывает exactly-once
remote delivery: accept до local receipt оставляет узкое at-least-once окно.
C0-F07 относится здесь только к backend/recovery; live operational proof
остаётся C5/C6. Эта матрица не принимает C4, deployment или готовность всего MVP1.
