## MVP2: точная цель

**Владелец с телефона пользуется Nobus Space как единым узнаваемым продуктом
PROстранства: быстро находит нужную задачу, ставит текстовую или голосовую задачу,
понимает требуемый следующий шаг и получает проверяемый результат/TXT.**

Это фирменное оформление и удобство уже разрешённых возможностей. Новых
источников данных, моделей, агентов, эффектов, второго Core или workflow engine
в MVP2 нет. Ремонт стабильности относится к M1-S1 и не скрывается за редизайном.

### Что входит

1. **Фирменная система.** Цвета, типографика, знак/аватар, поверхности, иконки,
   состояния и правила сообщений на основе актуального сайта/презентации
   PROстранства. Конкретные reference files, права на шрифты и assets фиксирует
   M2-G0; из старого описания нельзя выводить лицензию или точный действующий HEX.
2. **Mini App.** Единые список/карточка/создание/уточнение/результат/TXT; понятные
   empty/loading/error/offline/expired/UNKNOWN состояния, безопасный возврат
   после сворачивания, светлая и тёмная тема, доступность и мобильная клавиатура.
3. **Telegram.** Аватар и описание, menu entry, /start/help и согласованные
   сообщения о ходе работы, подтверждении голоса, уточнении, результате и файле.
   Оформляется то, что позволяет Telegram; шрифт сообщений нативного чата бот
   не заменяет. В Mini App шрифты и визуальная система управляются приложением.
4. **Понятные границы.** Короткие примеры только работающих задач, существующие
   лимиты и объяснения отказов. Переработка материала не означает исполнение
   вложенных команд. Голос по-прежнему подтверждается до создания задачи.
5. **Единая инструкция и выпуск.** Обновлённая существующая Word-памятка,
   версия UI/assets, связанные evidence, release note и раздельный live-статус.

Источник платформенных ограничений: [Telegram Mini Apps](https://core.telegram.org/bots/webapps)
и [Bot API](https://core.telegram.org/bots/api). При реализации проверяется
актуальная поддержка themeChanged, viewport/safe area и методов оформления.

### Что не входит

- Семантический compiler/ASR «заново», смена модели или автоматическое исполнение
  непроверенного голоса. Ошибка прежней функции возвращается в сопровождение MVP1.
- Общие вложения PDF/DOCX/XLSX/фото, новые выходные форматы, unlimited input,
  memory retrieval, Google/маркетплейсы, Business Notes или web tools.
- Реальная параллельность LLM-задач, новые adapter paths и Agent Registry.
- Перенос Core на VPS, SaaS/multi-user, платежи, Web IDE, терминал, self-deploy.
- Неподтверждённый workflow «предпросмотр всех текстовых задач → новая кнопка
  запуска». Используется действующая семантика; её изменение потребует отдельного
  решения, threat model и acceptance mapping в M2-G0.

### Измеримые критерии MVP2

Это предлагаемые цели, фиксируемые в M2-G0 до реализации, а не задним числом:

| ID | Критерий |
|---|---|
| M2-01 | После M1-S1 нет открытых блокеров стабильности; точные backend/runtime inputs известны |
| M2-02 | Владелец принял визуальную систему и источники бренда; один комплект tokens/assets для всех заявленных состояний |
| M2-03 | Все существующие основные пользовательские пути доступны через реальный Core; авторитет состояния не перенесён в frontend |
| M2-04 | На 320/360/390/768/1280px нет горизонтального overflow; проверены light/dark, клавиатура, focus, 200% text zoom, safe area и reduced motion. Основные target 44px; текст 4.5:1, крупный/значимые элементы 3:1 |
| M2-05 | При готовой сессии до ввода новой задачи не более двух действий; найденный последний результат/TXT — не более трёх. На рабочем контрольном устройстве owner проходит согласованные сценарии без подсказок; наблюдаемый результат протоколируется |
| M2-06 | Голос до confirm не создаёт задачи; lost ACK/reopen/expired session не создают дубль. Telegram и Mini App показывают один task/result/TXT, ожидаемые digest совпадают |
| M2-07 | Приёмка на iOS/Android Telegram, включая сворачивание и повторное открытие; если устройство недоступно, критерий остаётся непроверенным, desktop emulation его не заменяет |
| M2-08 | Нет новых внешних trackers/fonts/CDN без отдельного решения; initial own assets compressed ≤250KiB как стартовая цель, JS/CSS не растут >20% от измеренного M1-S1 base без обоснования. Не включать TXT/Telegram SDK/результаты в этот бюджет |
| M2-09 | Один frozen package прошёл проверки изменённых рисков и необходимые независимые reviews; exact code/assets/input/release/deploy bindings сохранены |
| M2-10 | Документация, Word-памятка и опубликованное после разрешения состояние соответствуют реально активированному UI; нет backend-only READY |

Критерии скорости не измеряются «по ощущениям». M2-G0 фиксирует устройство,
сетевой профиль и baseline. Любое изменение порогов согласуется до проверки,
с сохранением исходной цели и причины; нельзя подгонять критерий под FAIL.

## Пять Gate MVP2

| Gate | Результат | Зависимость | Промпт |
|---|---|---|---|
| M2-G0 | Принятый scope, источники бренда, journeys/метрики, архитектурные границы и план docs | M1-S1 и разрешение MVP2 | [Контракт](gates/mvp2/M2-G0-PROMPT.md) |
| M2-G1 | Согласованная визуальная система и интерактивный прототип всех состояний | Принятый M2-G0 | [Дизайн](gates/mvp2/M2-G1-PROMPT.md) |
| M2-G2 | Фирменный Mini App, подключённый к действующему Core | Принятый M2-G1 | [Mini App](gates/mvp2/M2-G2-PROMPT.md) |
| M2-G3 | Согласованный Telegram-путь, единая коммуникация, docs и цельный кандидат | Принятый M2-G2 | [Telegram и интеграция](gates/mvp2/M2-G3-PROMPT.md) |
| M2-G4 | Проверенный выпуск, owner acceptance и документированная активация | Принятый M2-G3, точные внешние разрешения | [Выпуск](gates/mvp2/M2-G4-PROMPT.md) |

Каждый Gate получает ровно одну задачу. Проверяющие и внутренние шаги остаются
в ней; пауза не создаёт нового Gate. Технически повторно используемые модули
проверяются только в затронутой границе. Не нужно ждать новой публикации после
каждой мелкой правки; на переходе нужен принятый точный predecessor SHA/tree.

Отдельные Gate не разрешают production effects по умолчанию. G1 не публикует
аватар; G2 не разворачивает UI; G3 не меняет меню в кабинете; G4 выполняет только
конкретно согласованные effects. Шаги публикации, восстановления и приёмки
внутри G4 не становятся новыми пользовательскими задачами.

**Источник планов — этот Markdown в Git. HTML16 — только производная для
просмотра.** Нельзя вручную менять статус только в HTML или вести вторую таблицу
Gate в Memory/Google. Для каждого утверждённого решения сохраняется короткая
привязка к owner decision либо новому forward ADR; accepted ADR не переписывается.

Рабочие runtime логи, raw payload, credentials, аудио, закрытые архивы и
необработанные Windows paths в публичную документацию не входят. Доказательства
публикуются санитизированно, с digest и понятной границей; закрытые данные не
переносятся из runtime «для полноты». Для документационного WIP допустимы только
локальные изменения; push/merge/publication остаются отдельным решением.

Подробная [механика публикации и актуализации](mvp2/DOCUMENTATION.md).
Стартовый [реестр Gate](gates/mvp2/REGISTRY.md) не содержит выдуманных task ids/SHA.

## Что остаётся после MVP2

MVP3 требует нового принятого архитектурного scope: точная матрица formats и
лимитов, защищённый ingress/выдача файлов, task/file/tenant isolation, минимум
две реально параллельные задачи, управление отменой и recovery, capability
contract сменного исполнителя. Второй настоящий adapter path нужен для заявления
«сменный исполнитель работает»; test double доказывает лишь контракт.

MVP4 — панель заранее подготовленных агентов. Reference workflows из исходного
замысла: отзывы/вопросы и ТЗ дизайнеру. Здесь они только примеры, их чужие проектные
данные не читались и готовность не проверялась. Manifest не даёт себе права:
launcher и capabilities разрешает Core. Третий совместимый агент — проверка
расширяемости; произвольные скрипты, multi-user и marketplace не подразумеваются.

Перенос runtime с ПК решается по измеренной доступности и требуемому режиму,
а не автоматически из-за одного инцидента. Нужны отдельные SLO, threat model,
recovery/cost decision и forward ADR; этот план не разрешает новую инфраструктуру.
