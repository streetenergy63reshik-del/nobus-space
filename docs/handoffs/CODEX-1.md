## Public API

`src.contracts` exports:

- `TaskContract` v1;
- `WorkerEvent` v1 with event/tenant/task/attempt/contract/worker bindings, a closed event enum and strict payload per event type;
- `VerificationBundle` v1;
- immutable result/contract-bound `HumanApprovalRecord` for L4 audit evidence;
- `RiskLevel`, verification status models and verifier identities.

`src.core` exports:

- `ALLOWED_TRANSITIONS`;
- `InMemoryPolicyStore.register_contract()` for duplicate idempotency rejection;
- `InMemoryPolicyStore.accept_event()` for event replay rejection and strictly increasing per-attempt sequences;
- `ensure_transition()`, `validate_verification_stage()` and `validate_completion()`;
- explicit policy exceptions.

Runtime `Task.id` and all related state interfaces use one UUID generated by `StateManager.create()`. A bundle can complete only its own task and only for the executor already stored on that task; a completion call cannot substitute the executor. `COMPLETED`, `FAILED` and `ESCALATE` records reject later changes to status, executor, result, bundle, error or context. `REJECTED` is audit-locked and permits only a clean atomic transition to `REWORK`.

`StateManager.update()` locks the executor from `DRAFT` through verification and human approval. Every update is built as isolated candidate data, fully validated through `Task.model_validate()`, checked by transition and bundle policy, and only then stored atomically. Invalid status, executor, result or context values therefore cannot partially mutate the saved task. A bundle is rejected at save time when its task or assigned executor does not match, even without a `COMPLETED` transition.

Security-critical contract/evidence sequences are immutable tuples. Policy/store boundaries revalidate Pydantic models so a mutated `WorkerEvent.payload` cannot add secret-bearing keys after initial validation. Idempotency is scoped by `(tenant_id, idempotency_key)`, and strict integer fields reject bool/float coercion.

WorkerEvent secret-key checks use a compact case/separator-insensitive form and reject camelCase, snake_case and kebab-case variants such as `apiKey`, `x-api-key`, `clientSecret` and `set-cookie` recursively. Values are not heuristically inspected.

L1/L2/L3 states require cumulative passed levels, evidence and independent identities at the transition that claims them. Partial bundles remain draft and can only add the next level; the full approved bundle is audit-locked after L3 and reused unchanged by human-approval and completion transitions.

A successful rule or worker result remains `DRAFT`; `DRAFT` atomically requires a non-empty result and frozen executor identity, and no existing worker path creates verification evidence automatically. Rule-based results use `core:rule-engine`. `LOW/MEDIUM` can complete after the explicit L1/L2/L3 chain. `HIGH/CRITICAL` must additionally pass `L3_APPROVED → WAITING_HUMAN → HUMAN_APPROVED → COMPLETED`; an external effect uses `HUMAN_APPROVED → EXECUTING → COMPLETED|FAILED|ESCALATE`. The record is first accepted only in the atomic `WAITING_HUMAN → HUMAN_APPROVED` update. Core rejects an approver equal to executor or any L1/L2/L3 verifier and binds `approved_at` to the inclusive interval between those two state-update timestamps.

Gate 1 stores the L4 approver identity, aware timestamp and evidence reference as an immutable audit record. It does not authenticate the claimed identity; Telegram/Core boundary authentication remains integration work for Gate 4. That future boundary must stamp `approved_at` with server time when the callback is received rather than trust a client timestamp.

## Unresolved risks and assumptions

- The legacy API still receives `UserRequest`; `TaskContract`, idempotency and WorkerEvent intake are not wired into Telegram/API ingress yet.
- `InMemoryPolicyStore` is process-local, non-persistent and not a concurrency solution; PostgreSQL enforcement remains a later gate.
- Runtime risk defaults to `LOW` unless supplied when the in-memory task is created; ingress-to-contract wiring remains a later gate.
- Allowed-path validation is lexical. A future worker boundary must resolve paths against its authorized workspace and re-check containment before filesystem access.
- WorkerEvent secret rejection detects secret-bearing keys, not arbitrary secret-like values; upstream minimization and redaction remain required.
- No real independent L1/L2/L3 executors exist yet. The implementation must not be described as production quality before review and integration.
