### Цель и критерии

1. Бот реально принимает разрешённую задачу и возвращает результат/TXT через
   существующие интерфейсы после контролируемого запуска.
2. Есть проверяемая причина каждого отказа. Core/relay exit, local/public
   readiness, startup timeout, planned stop и cleanup различимы без raw logs.
3. Ограниченное автоматическое восстановление доказано на реальном механизме
   Планировщика; permanent ошибки и исчерпание бюджета завершаются понятным STOP.
4. Сохранены все задачи/receipts/offset и новые записи между подготовкой и
   переключением; нет дублей, второй очереди, второго Core или blind retry.
5. Backup/recovery и затронутая безопасность проходят проверки; активная
   документация различает release и текущее runtime состояние.
6. После согласованного наблюдения нет необъяснённых остановок. Предложи окно 72 ч
   включённого ПК с минимум двумя плановыми backup; согласуй критерий и точную
   автоматику до запуска. Старый 15-минутный smoke не выдай за устойчивость.

### Полномочия и первый этап

После запуска владельцем этого промпта разрешены scoped read-only диагностика,
локальные правки кода/тестов/документации в изолированном рабочем checkout и
проверки синтетических fixtures без обращения к production/модели/ASR. Перед
правкой проверь status, сохрани чужой WIP и назначь зону файлов. Не трогай AGENTS,
глобальные skills/config, секретные хранилища, старые backups и recovery refs.

Publication/push/PR/merge/tag/release, deploy, изменение live Actions/служб,
включение Windows event logs, установка, реальные Scheduler fixtures и внешние
сообщения требуют отдельного текущего точного разрешения. Прежние C6 approvals
не действуют. Сначала подготовь конкретный план/кандидат и read-only evidence,
чтобы владелец утверждал готовое действие. Не запрашивай повторно то же уже данное
в этой задаче разрешение.

### Единый пакет

F01: выясни воспроизводимый механизм остановки. F02: сохрани существующий
санитизированный Core failure JSON и отдельные supervisor причины через
ограниченный доверенный протокол. F03: выясни отсутствие recovery при
RestartCount=10/PT1M; не утверждай, что бюджет исчерпан, без истории попыток.
Проследи scheduler pythonw→gated helper→Core/relay и exit propagation. Backup
умеет сам запускать enabled runtime и не доказывает работу retries.

F04: проверь подготовленное локальное исправление docs01/CURRENT/runbook и
включи его в согласованный пакет публикации; заново переписывать его не нужно. Не меняй
исторические C6 receipts и sealed sources. Документ 11 — runtime input; правка
требует нового input binding и относится к candidate, а не косметике.
D01: проверь зависимости по фактическому inventory; network metadata audit и
его сервис согласуй, не устанавливай инструменты и не обновляй пакеты вслепую.

Не перенаправляй сырой stdout/stderr в журналы. Достаточны timestamp, run identity,
стадия, типизированный error class/exit code, отдельные local/public результаты,
retry attempt/budget и cleanup outcome. Ограничь размер, ротацию, parser и отказ
записи. Никаких argv/env, payload, токенов, путей к credentials или текста задач.

Не заменяй diagnosis увеличением retries, новой моделью, отключением readiness,
автоматическим restore или переносом Core на VPS. Если старый первичный триггер
невосстановим, запиши UNKNOWN и используй разрешённый инструментированный запуск;
не заявляй причину по аналогии.

### Проверки и переходы

WIP: целевые RED→GREEN на найденный дефект, включая обрыв/неверный safe outcome,
Core exit, relay exit, local/public fail отдельно, deadline, stop и cleanup.
Детерминированные тесты имеют синтетические процессы/данные и отдельные имена
mutex/портов; не задевай production singleton.

Существующие 11 supervisor/readiness tests уже PASS на прежнем коде; после правок
повтори затронутые и зависимые, а не C0–C6 целиком. Для неизменных contracts
сохрани точные прежние SHA/evidence. Новый цельный Gate-кандидат заморозь один раз
с source/tree/assets/config/input digests и проведи обязательные независимые
L1/L2/L3 именно этой ревизии. Reviewer замечания сначала собери и классифицируй,
затем исправляй одним пакетом. Доказательства разных ревизий не смешивай.

Перед production предъяви единый план: точные refs/Actions/config, свежий backup,
baseline задач/receipts/offset, runtime inputs, бюджеты model/ASR/запусков,
ожидаемая пауза, rollback и проверяемый сигнал завершения. После разрешения
один Core/Job/lease, local/public/stock readiness, разрешённый реальный
результат/TXT и сверка сохранности. UNKNOWN эффект сначала сверяй, не повторяй.

Rollback только совместимых кода/config по отдельному разрешению; БД не
откатывать поверх новых accepted tasks. При неясной остановке не убивать все
python/ssh по имени. Без снятия production блокеров не ставь runtime READY.
