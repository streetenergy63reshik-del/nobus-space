## 2. Определение готового MVP-1

MVP-1 — owner-bound Telegram-оркестратор, который принимает обычные текстовые
и голосовые задачи, предоставляет полноценный owner-only Mini App, компилирует
задачи для закрытых specialist workers, безопасно работает с Google Workspace,
кодом и документами владельца на ПК, выполняет проверяемый анализ и возвращает
либо сохраняет результат в нужном формате.

MVP-1 принят, когда владелец одним естественным запросом может:

1. открыть Mini App и увидеть задачи, планы, approvals, agents, evidence и health;
2. поставить разработку Nobus через Telegram/Mini App и получить проверенный local candidate commit;
3. получить резюме «Заметок бизнеса»;
4. прочитать, создать или изменить Calendar event;
5. прочитать, создать, изменить или завершить Google Task;
6. найти документы на Google Drive и в `<OWNER_LIBRARY_ROOT>`;
7. проанализировать один или несколько Google/local документов;
8. отфильтровать данные по клиенту, артикулу, периоду и другим сущностям;
9. получить воспроизводимые расчёты и явно указанные источники;
10. получить Telegram text, JPEG либо self-contained HTML;
11. создать XLSX, DOCX, PDF, Google Docs или Google Sheets;
12. сохранить новый результат локально и/или на Google Drive;
13. контролируемо обновить существующий локальный или Google-документ;
14. видеть, какой specialist worker выполняет глубокую задачу;
15. получить понятную безопасную ошибку, а не общий необъяснимый отказ.

## 3. Неподвижные продуктовые принципы

### 3.1. Natural Language First

- основной интерфейс — обычный текст и голос;
- slash-команды — только операционный fallback;
- точная «магическая» формулировка не требуется;
- неоднозначность ведёт к одному понятному уточнению;
- кнопки допустимы для подтверждения/выбора, но не обязательны для начала
  продуктовой функции.

### 3.2. Codex управляет, Google усиливает

- Codex остаётся основным reasoning/control brain;
- Gemini применяется как Google-specialist для подходящего анализа и research;
- Nobus Core, а не модель, управляет правами, риском, idempotency и состоянием;
- модели не владеют OAuth, shell или ambient filesystem authority;
- внешние эффекты выполняют application-owned adapters.

### 3.3. Один Core — несколько specialist workers

- Nobus Core остаётся единственным orchestrator, policy/effect authority и приёмщиком результата;
- general, Google Workspace, research/analytics, content и development являются закрытыми worker profiles;
- workers не получают Telegram/Google credentials, ambient filesystem или право назначать себе capabilities;
- workers не вызывают друг друга напрямую: Core создаёт следующий durable `AgentDispatch` из проверенного результата;
- быстрые ответы и bounded public web research может выполнять general Codex worker;
- глубокие Google, analytics, content и development задачи маршрутизируются specialist profiles;
- external effects всегда выполняют application-owned adapters.

### 3.4. Google и ПК равноправны

Google Drive/Docs/Sheets и `<OWNER_LIBRARY_ROOT>` поддерживают одинаковый
продуктовый lifecycle:

`search → select → read → analyze → create → update → deliver`.

### 3.5. Безопасность не должна разрушать продукт

Проверки выполняются на доверенных границах и не превращаются в четыре
пользовательских клика. Точная owner-команда разрешает указанное обратимое
действие в заранее разрешённом scope. Необратимые и высокорисковые действия
сохраняют отдельный L4.

### 3.6. CURRENT отдельно от TARGET

Документ или ADR не доказывает работающий runtime. Готовность подтверждают
только точный commit, воспроизводимые тесты, L1/L2/L3, live evidence и
применимый L4.

### 3.7. Решения владельца по сервисам и authority

Точные Google/Codex/filesystem/monitoring/backup параметры закреплены в
[ADR 0019](adr/0019-owner-service-filesystem-and-runtime-decisions.md).
Они являются TARGET и не разрешают регистрацию, billing, OAuth, installation
или publication без отдельного Gate-bound L4.

## 4. Объём MVP-1

### Входит

- полноценный owner-only Telegram Mini App;
- ранний Linux Server Core/HTTPS foundation в Gate 2A;
- task/plan/approval/event/diff/evidence/artifact/agent/health views;
- closed Agent Registry и durable agent dispatch;
- Windows Development Worker под отдельной identity;
- Codex development в registered isolated worktree;
- exact tests/L1/L2/L3 и local candidate commit/ref;
- general, Google Workspace, research/analytics, content и development worker profiles;
- Telegram owner binding и один polling runner;
- durable queue, outbox, progress и restart recovery;
- локальная русская voice transcription;
- Natural Intent Kernel и scoped conversation context;
- Business Notes summary и task candidates;
- Calendar list/create/update;
- Tasks list/create/update/complete;
- public web research с evidence;
- Google Drive/Docs/Sheets read;
- owner library read под `<OWNER_LIBRARY_ROOT>`;
- Windows Local Library Bridge для server runtime;
- single- и multi-document analytics;
- cross-source Google + local analytics;
- Telegram text/JPEG/HTML;
- XLSX/DOCX/PDF artifacts;
- Google Docs/Sheets create;
- Drive upload нового разрешённого артефакта;
- snapshot/precondition-bound update там, где backend предоставляет строгий
  CAS; иначе новая версия/copy либо fail closed;
- L1/L2/L3, audit, backup, rollback и 72-часовой pilot.

### Не входит

- удаление реальных документов без отдельного L4;
- произвольное изменение sharing/access;
- отправка клиенту или третьей стороне без отдельного L4;
- деньги, покупки и платежи;
- массовые фоновые незапрошенные операции;
- arbitrary shell или прямой filesystem tool модели;
- чтение `<OWNER_LIBRARY_ROOT>\VPN данные`;
- коммерческий multi-tenant SaaS;
- автономное самоизменение политик, skills или prompts.

- отдельные Telegram-боты/оркестраторы для каждого specialist worker;
- свободный peer-to-peer agent chat без durable Core contracts;
- автономный self-deploy или изменение live release работающим Nobus;
- terminal/Web IDE/arbitrary shell в Mini App.

## 5. Целевая архитектура

```text
Telegram text/voice + owner-only Mini App
  -> Trusted Telegram/WebApp Ingress
  -> local voice transcription (если voice)
  -> IntentEnvelope
  -> Server Nobus Core / Policy / Durable Control+Effect Plane
       -> Agent Registry / AgentDispatch
       -> General Codex worker
       -> Google Workspace specialist
       -> Research & Analytics specialist
       -> Content Studio specialist
       -> Development specialist via Windows Development Worker
       -> Business Notes adapter
       -> Calendar / Tasks executors
       -> Google Document Gateway
       -> Windows Local Library Bridge
  -> normalized facts / proposed effect
  -> L1 / L2 / L3
  -> ResultComposer / Effect Executor
       -> Telegram text/JPEG/HTML
       -> Mini App task/evidence/artifact views
       -> local artifact
       -> Google Docs/Sheets/Drive

Windows Development Worker
  -> registered repository
  -> isolated worktree
  -> Codex plan/patch
  -> tests/evidence
  -> local candidate commit/ref
```

### 5.1. Server Nobus Core

Владеет:

- Telegram polling;
- HTTPS Mini App и same-origin Control API;
- durable queue/outbox/approval/effect/reconciliation;
- task/effect state;
- policy и audit;
- Agent Registry и specialist dispatch;
- Codex/Gemini gateways;
- Google Workspace adapters;
- verification orchestration;
- ResultComposer.

Server не получает SMB/share или произвольный filesystem-доступ к Windows-ПК.

### 5.2. Windows Development Worker

Development Worker:

- работает под отдельной service identity и не является Telegram runner;
- получает только closed signed development jobs через outbound authenticated transport;
- разрешает только registered repository, exact base и target paths;
- запускает Codex без production credentials и сети по умолчанию;
- создаёт один isolated worktree на task;
- выполняет exact test profiles и возвращает typed evidence;
- создаёт только local candidate commit/ref после action-bound approval;
- не выполняет remote/fetch/pull/push, deploy, service restart или live self-update.

### 5.3. Windows Local Library Bridge

Bridge:

- работает под отдельной минимальной identity;
- не является Telegram runner;
- не хранит Telegram или Google credentials;
- связывается с Core через device-bound mutual authentication;
- принимает только подписанный закрытый job;
- не публикует shell, PowerShell или arbitrary path API;
- проверяет root identity и containment перед каждой операцией;
- возвращает content/revision только в пределах job contract.

Когда Bridge offline, Google/Telegram продолжают работать. Локальная задача
становится `DEGRADED` либо безопасно ожидает reconnect; write не повторяется
вслепую.

## 6. Единые контракты

### IntentEnvelope

```yaml
schema: nobus.intent.v1
intent_id: uuid
tenant_id: trusted value
actor_identity: trusted owner binding
conversation_ref: tenant/chat/topic binding
ingress_digest: sha256
received_at: aware datetime
modality: text | voice
owner_text: bounded normalized text
voice: bounded ASR/confirmation binding | null
status: ready | needs_clarification | unsupported | rejected
domain: notes | calendar | tasks | documents | research | development | general
action: closed action enum
entities: [closed bounded entity]
period: explicit normalized range | null
source_scope: [bounded opaque selector]
requested_outputs: [telegram_text | jpeg | html | xlsx | docx | pdf | google_doc | google_sheet]
proposed_effects: [closed effect proposal]
confidence: integer basis points 0..10000
ambiguities: [closed bounded ambiguity]
clarification: one bounded question | null
context: scoped conversation binding
policy_version: string
route_registry_version: string
intent_revision: sha256 excluding itself
```

Trusted identity, policy, route, effect и adapter повторно выводятся Core; model
proposal не является authority. Exact nested types и validators определяет Gate 1.

Следующие сокращённые фрагменты — продуктовые проекции, а не параллельные wire
schemas. Exact `IntentEnvelope` принадлежит Gate 1; document contracts и
`AnalysisRequest` — Gate 2; effect contracts — Gate 4; analytics — Gate 6;
artifacts/receipts — Gate 7.

### DocumentRef

```yaml
schema: nobus.document_ref.v1
backend: local | google
tenant_id: trusted value
project_ref: string
client_ref: string | null
source_id: opaque Core/Bridge-minted handle
revision: sha256 digest | google revision
media_type: string
classification: public | internal | confidential | restricted
provenance: bounded object
```

### DocumentQuery

Описывает source, project/client, file/folder hints, period, media types и
maximum candidates. Поиск metadata-first; содержимое не читается до selection.
Drive-wide metadata discovery не является source authority: выбранный item
получает exact project/client-bound file/folder registry/ref до content read.

### DocumentReadPlan

Описывает exact `DocumentRef`, ranges/pages/sheets, byte/character limits и
purpose. Перед чтением revision/digest перепроверяется.

### AnalysisRequest

Продуктовая проекция exact Gate 2 wire schema:

```yaml
analysis_id: opaque id
idempotency_key: digest-bound key
read_plan_digest: sha256
sources: [exact DocumentRef]
question: bounded string
sku_or_articles: [canonical registry ref]
period: DocumentPeriod | null
metrics: [closed metric request]
grouping: [closed dimension]
calculation_rules: [versioned rule ref]
requested_outputs: [closed output]
limitations: [safe reason]
processing_policy_ref: exact versioned ref
limits: closed monotonic ceilings
maximum_classification: public | internal | confidential | restricted
```

Общие identity/binding fields и `contract_digest` определяет Gate 2. Gate 6
принимает этот объект без второго варианта `AnalysisRequest` и создаёт только
внутренний `AnalysisExecutionPlan`.

### ArtifactPlan

Описывает title, format, content sections, normalized tables/charts,
provenance, target backend и destination hint.

### DocumentWritePlan

```yaml
backend: local | google
operation: create | update
target: exact opaque output or provider destination reference
expected_revision: digest/revision | null
artifact_digest: sha256
collision_policy: new_version | ask
snapshot_required: boolean
idempotency_key: string
approval_binding: exact owner request or preview confirmation
```

Неизвестные поля и enum запрещены. Durable state не хранит открытый текст
локального документа без отдельного зашифрованного контракта.

## 7. Owner library `<OWNER_LIBRARY_ROOT>`

`<OWNER_LIBRARY_ROOT>` is an opaque deployment binding stored in protected local
configuration. It is bound to the owner-selected Windows library root during
Gate 2/5 activation, but its absolute value never enters model prompts, public
contracts, artifacts, logs, manifests or evidence packs.

### 7.1. Source scope

Owner root один: `<OWNER_LIBRARY_ROOT>`.

Фактические project/client roots задаёт versioned source registry. Модель не
получает абсолютный owner root. Metadata index ограничен по количеству entries,
кандидатов и времени.

Владелец связал `<OWNER_LIBRARY_ROOT>` с `C:\Хранилище\АГЕНТ`. Обычные
бизнес-документы и рабочие деревья исходного кода внутри root могут входить в
versioned registry. Это не создаёт один ambient cross-project scope: каждый
request сохраняет project/client binding, а явная cross-project задача
получает отдельный scoped contract. Agent в MVP-1 — execution role внутри этого
scope, не отдельная authority boundary.

### 7.2. Always-deny

- `<OWNER_LIBRARY_ROOT>\VPN данные`;
- ambient/нерегистрированное чтение `<OWNER_LIBRARY_ROOT>\Системные`;
  allowlisted ordinary code/tool resources доступны только через registry;
- `Nobus memory backups`;
- внутренние `.git` objects/config/refs, `.runtime`, `.venv`, caches, logs и
  temp; рабочее дерево кода доступно только через code workflow;
- secret/token/credential-like names;
- files with `NumberOfLinks > 1` и доказанные hard-link aliases без
  исключений; `NumberOfLinks = 1` допустим;
- symlink, junction и другие reparse points.

`Nobus memory` обслуживается только curated memory adapter.

### 7.3. Output scope

Локальная запись разрешена только в versioned output registry. Destination
выводится из project/client binding, а не придумывается моделью.

Новый путь создаётся без второй кнопки, если точная owner-команда содержит
неизменившиеся format/destination. Collision не перезаписывает оригинал:
создаётся новая версия либо запрашивается выбор.

Update требует snapshot, digest CAS, diff preview, atomic replace и readback.
Удаление не входит в обычный контур.

Для бизнес-документов default — новая numbered version. Для исходного кода
pre-state manifest связывает HEAD/ref, index/worktree state и target-path
Digests; пересечение с чужими staged/uncommitted paths вызывает fail-closed.
Кандидат проверяется в disposable no-network/no-credentials OS sandbox на exact
base HEAD и проходит L1/L2/L3. L4 связывает pre-state, exact patch,
file/delete manifest и evidence. Trusted exact-argv Git plumbing adapter
отключает hooks/signing/pager/fsmonitor/external filters, scrubbed inherited
`GIT_*`, запрещает alternates/grafts/replace refs и требует containment каждого
явного Git path. Он создаёт commit/candidate ref через CAS и не меняет caller
worktree/index. Active branch изменяется только
при exact clean precondition; post-commit tree/diff/readback обязателен. Adapter
не выполняет config/remotes/submodules или Git network.

## 8. Google Workspace

### 8.1. Read plane

- Calendar/Tasks/Drive/Docs/Sheets читаются через официальные API;
- Drive discovery охватывает My Drive и обычные shared-with-owner items;
  обязательная поддержка Workspace Shared Drives в MVP-1 не заявляется;
- Drive search metadata-first;
- Google Docs читается структурированно либо через проверенный export;
- Google Sheets читается ranges, а не полным blind export;
- API/MCP transport failure не интерпретируется как отсутствие данных.

### 8.2. Intelligence plane

- Codex — основной planner/analyst;
- production candidate — persistent официальный Codex app-server/SDK из
  поставки Codex CLI через существующий доступ владельца; OpenAI API не
  включается автоматически;
- Gemini — специализированный Google worker;
- Preview Google agents только за feature flag;
- provider outage не блокирует Telegram polling;
- read-only fallback bounded;
- costs и retention контролируются Core.

### 8.3. Write plane

Поддерживаются:

- Calendar create/update;
- Tasks create/update/complete;
- Google Docs create;
- Google Sheets create;
- Drive upload нового HTML/JPEG/XLSX/DOCX/PDF;
- revision-bound update существующего Google Docs;
- update существующего Google Sheets или Drive blob только при отдельно
  доказанном строгом precondition; иначе новая version/copy либо fail closed.

Если exact payload/target изменился после исходного owner request, Core обязан
показать preview и получить естественное подтверждение. Unknown write outcome
сначала проходит reconciliation; blind retry запрещён.

Sharing/access changes и delete требуют отдельного L4.

## 9. Документная аналитика

### 9.1. Query planning

До чтения формируется точный plan: client, SKU/article, period, sources,
metrics, grouping и output. Огромный файл не передаётся модели целиком.

### 9.2. Extraction

Предпочтение:

1. structured values/ranges;
2. локальное детерминированное извлечение;
3. bounded excerpts;
4. OCR только для scanned PDF и только после отдельного corpus gate.

### 9.3. Calculations

Формулы выполняются отдельно от narrative. L1 проверяет типы, диапазоны,
тоталы и invariants. L2 независимо пересчитывает. L3 ищет ложную причинность,
scope leak и подмену отсутствующих данных.

### 9.4. Conflict handling

Расхождение источников не разрешается молча. Результат показывает:

- какие значения расходятся;
- из каких files/sheets/pages они получены;
- какая revision использована;
- что требуется от владельца.

### 9.5. Result formats

Короткий вопрос получает Telegram text. Сложный результат может вернуть JPEG и
self-contained HTML. Один HTML source используется также для JPEG screenshot и
PDF render; XLSX/DOCX строятся из тех же normalized facts.

## 11. Отказы и поведение

| Отказ | Поведение |
|---|---|
| Mini App auth/session invalid | Denied; task/effect не создаются |
| Development Worker offline | Development DEGRADED; остальные domain routes продолжают работу |
| Code mutation outcome unknown | Journal/readback reconciliation; no blind retry |
| Intent ambiguous | Уточнить, не исполнять |
| Google provider unavailable | Bounded read fallback или безопасный failure |
| Google write outcome unknown | Reconciliation до любого retry |
| Bridge offline | Local DEGRADED; Google/Telegram продолжают работу |
| Local file revision changed | Conflict; не перезаписывать |
| Google Docs/Calendar revision changed | Conflict; новый preview |
| Sheets/Drive strict CAS недоступен | Новая version/copy либо fail closed |
| Secret/DLP boundary | Fail closed, без model transfer |
| Prompt injection в документе | Данные без tools/authority |
| Duplicate Telegram/update/job | Idempotent replay |
| Orphan PENDING | Reconcile; composite health не PASS |
| Второй Telegram runner | Publication blocked |
| Technical release failure | Stop + verified rollback; no automatic retry |
| Процедурная ошибка smoke | Исправить на том же runner без rollback |
| Неоднозначная ошибка | Остановиться и запросить владельца |

## 13. Gate handoff contract

Каждая отдельная задача Gate обязана вернуть:

- Gate number/name;
- exact base commit;
- exact result commit;
- manifest изменённых файлов;
- CURRENT before/after;
- TARGET remaining;
- deterministic L1 evidence;
- independent L2 evidence;
- adversarial L3 evidence;
- применённый L4 и receipts;
- backups/migrations/external effects;
- open risks;
- `READY` либо `BLOCKED`;
- точные входы для следующего Gate.

Rework аннулирует evidence предыдущей revision. Следующий Gate не принимает
устное «готово» без handoff.

## 15. Definition of Done

MVP-1 не считается готовым, пока:

- Gate 0–8, включая обязательный Gate 2A, не имеют accepted handoff;
- exact release commit не зафиксирован;
- L1/L2/L3 не PASS;
- server/Bridge/Google/runtime composite health не PASS;
- polling readiness не свежий;
- orphan PENDING или неизвестный write outcome не reconciled;
- хотя бы один обязательный natural smoke не пройден;
- backup/rollback не проверены;
- 72-часовой pilot не завершён;
- TARGET ошибочно описывается как CURRENT.

## 16. Change control

Изменение принципов Natural Language First, Google/local parity, trust
boundaries, матрицы полномочий, Gate sequence либо Definition of Done требует:

1. impact analysis;
2. изменения или нового ADR;
3. обновления этого документа;
4. проверки ссылок/терминов/контрактов;
5. независимых L2/L3;
6. явного одобрения владельца, если меняются права, внешние действия, стоимость,
   удаление или production behavior.

Один баг или успешный кейс не меняет этот эталон автоматически.
