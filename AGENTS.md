# Правила разработки Nobus Space

Действуют правила всех родительских `AGENTS.md`. Этот файл уточняет работу в каноническом репозитории `nobus-orchestrator-dev`.

## Перед изменениями

1. Прочитать [docs/README.md](docs/README.md), [текущий статус](docs/handoffs/CURRENT-STATUS.md) и только релевантные документы/ADR затрагиваемой области.
2. Проверить `git status` и не изменять чужие незавершённые файлы без согласованной зоны владения.
3. Сформулировать короткий контракт результата: бизнес-цель, границы, критерии приёмки и риск.

## Git-канон

- Этот репозиторий — источник истины для кода, тестов, конфигурации, ADR, текущего статуса и постоянной документации Nobus Space.
- Канон принятой опубликованной истории — защищённая `main` и релизные теги GitHub `streetenergy63reshik-del/nobus-space`. Локальная ветка и незакоммиченные изменения остаются WIP до принятого PR/merge.
- Nobus Memory хранит только указатель, краткий статус, решения и свежесть; при расхождении побеждает точная Git revision и её проверки.

## Код и архитектура

- Репозиторий — единственное место развития MVP. Старые каталоги используются только как read-only источник до их контролируемого удаления.
- Различать `CURRENT` и `TARGET`; документация не превращает целевое поведение в реализованное.
- Trust boundary, tenant isolation, idempotency, evidence binding, audit trail и обработку ошибок нельзя упрощать ради сокращения кода.
- Предпочитать стандартную библиотеку и существующие зависимости. Новая зависимость требует доказанной необходимости, точной версии и проверки лицензии/уязвимостей.
- Не создавать speculative framework, параллельные модели одного контракта или совместимость без реального потребителя.
- Исключения, ответы API и журналы не должны раскрывать секреты, сырые payload, аудио, локальные пути и данные другого tenant.

## Git и зоны работы

- Один исполнитель — одна явно назначенная зона файлов; параллельные зоны не пересекаются.
- Локальный WIP и checkpoint commit допустимы после относящихся к изменению целевых проверок. Полный независимый L1/L2/L3 нужен по замороженному gate/release-кандидату, а не перед каждым commit.
- Push, подключение remote, deploy, публикация и внешние записи выполнять только в явно разрешённом объёме. Формальный L4 не добавлять, если действие не удаляет данные и не является критическим изменением кабинета маркетплейса.
- Не добавлять `.env`, credentials, токены, cookies, временные audio, кэши, логи и локальные настройки.

## Готовность

- Во время WIP тестировать изменённый модуль минимальным относящимся набором. Полный набор запускать на цельном checkpoint/gate или когда риск изменения этого требует.
- Проверять формат/ссылки/границы данных и негативные сценарии, а не только happy path.
- До независимых L2/L3 цельный gate/release-кандидат остаётся `DRAFT`; обычный WIP не объявлять проверенным релизом.
- При изменении bytes замороженного кандидата доказательства старой ревизии не переиспользовать. Микроправка WIP не запускает новый полный цикл.
- Обновлять `docs/handoffs/CURRENT-STATUS.md` на границе цельного checkpoint/gate по воспроизводимым фактам. Quality case записывать только для принятого gate/release или долговечного переиспользуемого вывода.
