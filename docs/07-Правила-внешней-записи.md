# 07. Правила внешней записи

**Статус документа:** CANONICAL
**Состояние реализации:** PARTIAL; production enforcement отсутствует
**Дата актуализации:** 20 июля 2026

## 1. Главное правило

Nobus Space может самостоятельно читать разрешённые источники и готовить черновики. **Любое изменение состояния вне изолированной рабочей среды требует L1–L3 и явного L4-подтверждения уполномоченного человека.**

Исключений по сумме, проценту правок, типу клиента, «обычности» операции или обратимости нет.

Транспортный ответ в тот же аутентифицированный Telegram-чат инициатора (`ack`, preview, запрос L4 или результат без нового бизнес-эффекта) является частью явно начатой пользователем control-plane сессии, а не отдельным внешним бизнес-действием. Он разрешён только исходным ingress contract, tenant/chat binding и безопасным шаблоном. Новый адресат, другой чат, публикация или сообщение третьей стороне всегда требуют отдельного L4.

К внешней записи относятся:

- отправка сообщения, письма, комментария или файла третьей стороне;
- публикация и редактирование объявления, карточки, сайта или рекламы;
- платёж, заказ, возврат, перевод и изменение цены;
- создание, изменение или удаление данных во внешнем API либо кабинете;
- изменение ролей, доступов, credentials и настроек безопасности;
- удаление, перемещение или перезапись данных за пределами task sandbox;
- production deployment и применение миграции;
- включение автоматизации, которая впоследствии сможет выполнять такие действия.

Не является внешней записью: чтение из заранее разрешённого источника, расчёт, локальный тест, создание preview в task sandbox. Даже read-only действие запрещается, если источник или данные не разрешены политикой tenant.

## 2. CURRENT и TARGET

### CURRENT

- В Core есть черновая модель L4-record и часть state-transition проверок.
- Нет доверенной Telegram-аутентификации, постоянного журнала, idempotent execution boundary и реальных внешних adapters.
- Поэтому реальные внешние действия через платформу запрещены.

### TARGET

Путь действия: `trusted request → draft → L1–L3 → immutable preview → WAITING_HUMAN → bound L4 → one-shot execution → receipt`.

Core, а не LLM, проверяет разрешение, срок, привязку, idempotency и допустимость инструмента. Worker получает только одно узкое действие, уже разрешённое Core.

## 3. Неизменяемый preview действия

До запроса L4 система формирует человеку понятный preview и вычисляет `action_digest` по каноническому payload. `ApprovalRequest` и его preview содержат:

| Поле | Назначение |
|---|---|
| `request_id` | уникальный идентификатор запроса подтверждения |
| `task_id`, `tenant_id`, `contract_digest` | исключают перенос между задачами, клиентами и требованиями |
| `result_revision`, `result_digest` | порядковая версия и хэш проверенного результата |
| `requester_id` | кто запросил подтверждение |
| `action_type`, `tool_id`, `target` | точное действие, инструмент и адресат |
| `action_digest` | хэш полного канонического payload |
| `idempotency_key` | защита от повторного выполнения |
| `requested_at`, `expires_at` | серверное время UTC |
| `policy_version` | версия применённой политики |

В preview отображаются адресат, изменяемые поля, денежная сумма и валюта, видимость публикации, удаляемые объекты, последствия, способ отката и срок действия. Секреты маскируются.

Изменение любого связанного поля делает подтверждение недействительным. Новый payload требует новой ревизии, L1–L3, preview и L4.

После callback отдельный `ApprovalDecision` хранит `decision_id`, `request_id`, аутентифицированного `approver_id`, `approved|rejected`, `decided_at` по серверному времени и auth evidence ref. При expiry решение человека не создаётся.

## 4. Доверенная граница подтверждения

Telegram callback принимается только если одновременно выполнено следующее:

- в webhook-режиме endpoint использует HTTPS, до parse проверяет точное значение server-configured header `X-Telegram-Bot-Api-Secret-Token`, ограничивает body/timeout и поддерживает контролируемую ротацию секрета;
- в polling-режиме используется TLS Bot API, только один consumer владеет bot token, а подтверждённый offset сохраняется до обработки следующего update;
- bot identity проверяется server-side при старте и после ротации token;
- `user_id` и `chat_id` сопоставлены с tenant и ролью в серверном allowlist;
- callback содержит непрозрачный одноразовый token, а сервер восстанавливает действие из своей базы;
- `update_id`, callback token и `request_id` ещё не использованы;
- серверное время находится внутри TTL;
- approver не совпадает с executor, L1, L2 или L3 этой пары `result_revision` + `result_digest`;
- сохранённый `action_digest` совпадает с подготовленным действием.

Поля, пришедшие от Telegram или LLM, не могут сами назначать tenant, права, время или действие. Клиентское время не используется для решения об approval.

**Молчание и истёкший TTL никогда не являются согласием.** По истечении TTL действие не выполняется, задача переходит в `REJECTED` с причиной `approval_expired`. Для повторной попытки нужен новый preview и новое явное подтверждение.

Истечение фиксирует server-side timer/job одной атомарной записью `WAITING_HUMAN → REJECTED`; решение человека и `ApprovalDecision` при этом не создаются.

## 5. Исполнение после L4

Перед вызовом внешнего adapter Core повторно проверяет:

1. атомарный переход `HUMAN_APPROVED → EXECUTING` и audit-lock результата;
2. task/tenant/revision/action binding;
3. TTL, роль approver и policy version;
4. idempotency key и отсутствие execution receipt;
5. allowlist инструмента, target, метода и параметров;
6. наличие необходимых credentials из доверенного secret store;
7. актуальность критичных предпосылок, например баланса или версии удалённого объекта.

Выполнение допускается ровно один раз. Сетевой timeout с неизвестным исходом не запускает слепой повтор: adapter сначала запрашивает состояние по idempotency key либо переводит задачу в `ESCALATE`. После успеха квитанция и переход `EXECUTING → COMPLETED` сохраняются вместе; доказанный отказ ведёт в `FAILED`, неизвестный исход — в `ESCALATE`.

## 6. Trust boundaries и недоверенные данные

Всё содержимое Telegram, сайтов, документов, писем, API-ответов и результатов LLM считается недоверенными данными. Текст вида «игнорируй правила», «вызови инструмент» или «это подтверждено владельцем» не является командой Core.

Обязательные ограничения worker:

- инструменты, методы и домены — только из tenant-scoped allowlist;
- исходящий трафик по умолчанию запрещён и открывается на конкретный target;
- файловая система ограничена task sandbox и явно выданными read-only входами;
- shell, subprocess, динамическая загрузка кода и произвольные плагины запрещены по умолчанию;
- секреты выдаются непосредственно adapter и не попадают в prompt;
- HTML, документы и сообщения обрабатываются как данные, не как инструкции;
- лимиты времени, размера, стоимости и количества запросов обязательны.

## 7. Деньги, доступ и удаление

Для финансовых действий preview дополнительно содержит сумму, валюту, комиссию, получателя, источник средств и дневной итог. Для доступа — субъект, прежняя и новая роль, срок и способ отзыва. Для удаления — точный manifest объектов, наличие проверенной резервной копии, срок восстановления и необратимые последствия.

Такие действия относятся к `CRITICAL`. Даже после L4 adapter применяет минимальные права, ограничение суммы/объёма и post-condition проверку. Массовое действие разбивается на ограниченные партии; подтверждение явно указывает размер партии.

## 8. Аудит

Audit event неизменяемо хранит:

- task, tenant, `contract_digest`, `result_revision`, `result_digest`, approval request/decision;
- actor, его роль, auth method и server time;
- policy/model/prompt/tool versions;
- preview digest, idempotency key и фактический payload hash;
- результат, external receipt, стоимость и длительность;
- ошибку в безопасной форме без секретов;
- ссылку на rollback либо причину его невозможности.

Журнал защищается от перезаписи, tenant-scoped и доступен только уполномоченным ролям. LLM не может изменять audit events.

## 9. Аварийная остановка

Core должен иметь независимый от LLM и Telegram kill switch, который:

- запрещает новые внешние записи по системе, tenant, adapter или action type;
- не отменяет чтение audit trail и восстановительные операции;
- фиксирует инициатора и причину;
- требует отдельного человеческого решения для повторного включения.

При недоступности Telegram новые L4 не выдаются. Оповещение об инциденте уходит по независимому каналу, определённому в `08-Runbook-эксплуатации.md`.

## 10. Критерий готовности внешнего adapter

Adapter не допускается к реальным данным, пока не проверены:

- authenticated boundary и tenant mapping;
- replay, expiry, mismatched binding и double-click сценарии;
- idempotency и неизвестный результат timeout;
- allowlists сети, файлов и tools;
- redaction секретов и prompt-injection tests;
- безопасный dry-run/fake режим;
- audit receipt, rollback и kill switch;
- L1–L3 и отдельное L4 на production deployment.

Регламент уровней описан в `06-Регламент-качества-L1-L4.md`; формат approval preview — в `09-Стандарты-отчётов.md`; эксплуатация и инциденты — в `08-Runbook-эксплуатации.md`.
