# Аудит готовности и стабильности Nobus Space MVP1

13 сентября 2026. Локальный результат архитектора; не опубликован и не является
новой приёмкой C6. Проверяемый продукт: `82003c03d8a36015703472b472640ab4021fb416`.
Опубликованная main: `88e58c8866db2384423f2b154df901a2e4af6c48`.

## Вердикт

**MVP1 принят как выпущенный продукт v1.0.2, но сейчас непригоден для реальной
работы из-за недоступного запуска. Стабильность постоянной эксплуатации не
подтверждена.** Нужен один Gate сопровождения M1-S1 перед реализацией MVP2.

Это не повтор C6: сохраняются принятая версия, исторические L1–L3 и реальные
пользовательские сценарии. Новое основание — повторяющийся эксплуатационный
сбой после приёмки. Код и runtime пока не исправлялись; устаревшая проекция
документов исправлена локально. Подготовлен
[промпт M1-S1](../gates/mvp1-maintenance/M1-S1-PROMPT.md).

## Область и метод

Проверены Git/GitHub main/tag/release, опубликованные C0–C6/ADR/runbook,
read-only состояние runtime, журналы, задания Планировщика, HTTP, процессы,
polling lease, четыре SQLite, безопасные счётчики и сегодняшняя копия.
Код просмотрен на границах supervisor, polling, HTTP/auth, worker, recovery,
семантики и выдачи артефактов. Отдельно выполнен статический security-проход
766 файлов Git-снимка; private runtime, credentials и local config исключены.

Полный набор C0–C6 не запускался. Из-за нового сбоя выполнены только 11
относящихся проверок supervisor/readiness; 32 других теста этого файла не выбраны.
Оценка — технический CHECKPOINT: она не сертифицирует release или безопасность
всей инфраструктуры. Новые модельные, ASR, пользовательские и платные вызовы,
полный restore, нагрузка, публикация, deploy и перезапуск не выполнялись.

## Подтверждённые находки и единый пакет правок

### F01 — P1: действующий экземпляр недоступен

Наблюдение 21:13–21:18 МСК: Core/supervisor/relay отсутствуют, listener 8765 нет,
active lease=0, local ConnectionRefusedError, public 502. В 21:27 штатная
readiness снова FAIL; последняя starting 03:31:06, runtime_failed 13:28:54 МСК.
Аналогичные завершения есть 10–12 сентября. Main включён и Ready, а не Running.

Класс: эксплуатационный отказ; первичный implementation/environment trigger
не установлен. Исправление: безопасная диагностика и устранение доказанного
триггера; контролируемый запуск с сохранением состояния и проверкой конечного
пользовательского результата. Не переустанавливать всё и не повторять миграцию.

### F02 — P1: процесс теряет причину завершения

`scripts/run_nobus_space_live.py:122,130`: stdout/stderr детей идут в DEVNULL.
`:259–277`: Core exit, relay exit и readiness failure сводятся к return 1;
`:409`: сохраняется только runtime_failed. При этом Core уже печатает безопасный
типизированный JSON с кодом ошибки в `scripts/run_telegram_mvp1.py:758–790`, но
этот вывод не сохраняется. Старые runner-core/runner-relay логи датированы 1–2
сентября и не описывают C6 runtime.

Класс: подтверждённый дефект наблюдаемости. Исправление: ограниченный безопасный
канал исхода Core и структурированные события supervisor с run identity,
фазой, exit code, отдельными local/public исходами и cleanup outcome. Не
перенаправлять сырой stderr в файл. Проверить redaction, размер, отказ записи,
неточность/обрыв сообщения и отсутствие новой возможности исполнения.

### F03 — P1: восстановление через Планировщик не доказано

Настроены RestartCount=10/PT1M, logon trigger, unlimited ExecutionTimeLimit,
IgnoreNew. Runtime остаётся остановленным; новых starting после последней
ошибки нет. Журнал Microsoft-Windows-TaskScheduler/Operational выключен.
Health только пишет FAIL; он не запускает Core. Утренние starting совпадают с
backup, который по своему контракту запускает enabled остановленный runtime.

Класс: эксплуатационный пробел и недостаточное доказательство recovery.
Причина — исчерпанный бюджет, особенности запуска, exit propagation или иной
фактор — пока UNKNOWN. Исправление: доказать поведение реального Scheduler на
изолированном задании и проследить wrapper/child lifecycle; затем минимально
исправить подтверждённую причину. Включение журнала Windows, создание тестового
задания и изменения production Actions требуют точного разрешения. Не
увеличивать число повторов и не превращать Health в бесконечный restart loop.

### F04 — P2: активные документы смешивают статусы разных дат

В опубликованной main `docs/01-Единый-документ-проекта.md:52` говорит, что активация, приёмка и выпуск
C6 ещё впереди, при этом первая строка уже фиксирует принятие. CURRENT и runbook
имеют датированные утверждения «работает» от 9 сентября, но не отражают более
поздний runtime incident. ADR0022 содержит исторический implementation status;
его нормативное решение остаётся действующим.

Класс: устаревшая проекция, не откат релиза. Исправление: один CURRENT с отдельными
release/runtime/incident/next-action и временем наблюдения; убрать конфликтующую
активную строку docs01, связать runbook с текущим incident. Исторические C6 receipts
не переписывать. Документ 11 является входом принятого runtime: не менять его
«заодно»; если потребуется — отдельно включить изменение в candidate/input binding.

В этой работе локально исправлены docs01, README, CURRENT, runbook и индекс Gate.
F04 имеет статус **LOCAL FIX / NOT PUBLISHED**. Дальше требуется согласованная
публикация уже подготовленной правки и readback; повторно писать документы не нужно.

### Открытая проверка D01 — зависимости

Автоматический сканер не проверяет Python CVE. Прямые версии закреплены, но это
не полная transitive lock и не свидетельство отсутствия уязвимостей. Перед новой
release-приёмкой нужен scoped inventory фактического окружения и актуальная
проверка advisory, без вывода приватных index URLs/credentials и установки пакетов
наугад. Отправку metadata стороннему сервису сначала согласовать. Не обновлять
зависимости без доказанного риска и воспроизводимой проверки совместимости.

## Security-проход: классификация результатов

[Исходный отчёт](System/MVP1-STATIC-SCAN.md) содержит 40 эвристических сигналов:
6 critical и 34 warning. Это **не 40 подтверждённых уязвимостей**.

| Сигналы | Итог ручной проверки |
|---|---|
| 6 secret critical | tests/test_codex_patch.py и tests/test_owner_files.py: повторяющиеся/примерные строки, алфавитный placeholder или один PEM header; тесты детектора, не подтверждённые живые credentials |
| 3 generic secret | Константы тестов runtime/effect delivery, синтетические строки; не текущие credentials |
| 14 SQL f-string | 4 в production maintenance: имена проходят fullmatch `[a-z_]+`, ORDER BY состоит из сгенерированных номеров. Остальные — контролируемые test fixtures/collectors. Свободный пользовательский SQL не выявлен |
| 1 rate-limit | Ложная эвристика по тестовому маршруту и отсутствию библиотеки. Production `_ResourceBoundary` имеет собственные token buckets, MAX_ACTIVE=8 и пределы запросов |
| 15 max_tokens | Эвристика совпадает с imports/config/тестами SDK. Production использует deadline, scoped capabilities, bounds и Core admission; признак не доказывает открытый платный endpoint. Отдельный финансовый лимит аккаунта не проверялся |
| 1 dependencies | Реально не выполненная проверка; D01 остаётся открытой |

Примером ручного подтверждения служит цепочка Mini App: server-side identity и
session → scoped task/artifact projection. Client не назначает tenant/role.
API и readiness не кэшируются; CSP ограничивает origin; вход/выход/параллельные
HTTP запросы ограничены. Это обзор конкретных границ, не полный пентест.

Прямые package versions и SDK imports не являются причиной runtime_failed без
соответствующего evidence. Модель не меняется для обхода невыясненного сбоя.

live-runtime и работу реального Scheduler retry.

## Приёмка M1-S1

До допуска MVP2 должны быть выполнены все применимые пункты:

1. Причина нового наблюдаемого сбоя установлена и воспроизведена либо честно
   зафиксировано, почему старый триггер невосстановим; доступна диагностика всех
   ветвей завершения. UNKNOWN нельзя переименовать в «исправлено».
2. Ограниченный recovery работает после проверенного transient отказа; permanent
   отказ оставляет понятный остановленный статус. Не более согласованного бюджета.
3. После согласованной активации один Core/Job/poller, local/public/stock готовность,
   реальный разрешённый результат/TXT, неизменные receipts/offset и сохранность
   новых задач. Никакого слепого retry неизвестных effects.
4. Проверен свежий backup и сохранность состояния после затронутого recovery.
   Полный старый restore не повторять, если его контракт/схема/путь не затронуты.
5. Предлагаемое окно стабильности — 72 часа включённого ПК и активной сессии,
   с минимум двумя плановыми backup и достаточными наблюдениями готовности.
   Цель: нет необъяснённых остановок; каждый injected/transient отказ завершается
   предсказуемым recovery или безопасным STOP с причиной. Это новый предложенный
   критерий, согласуется до live-испытания; не SLA 24/7.
6. Выполнен D01 в разрешённой границе или дан явный обоснованный release verdict
   с его ограничением; активные документы правдивы. Новый source/assets/config
   связан с проверками и действительными разрешениями.

Автоматизацию наблюдения не создавали. Сокращать окно допустимо только по принятому
решению с объяснением, каким проверенным механизмом заменяется многосуточное
наблюдение. Одного успешного запуска или 15 минут HTTP 200 недостаточно.
