## 1. Продукт и первый результат

Nobus Space — owner-bound система постановки, выполнения и проверяемого
завершения задач через Telegram. MVP-1 соединяет Telegram-оркестратор и тонкий
Telegram Mini App с одним существующим локальным Core/Codex runtime.

Продуктовый результат:

```text
владелец открывает Mini App из Telegram
  -> backend проверяет Telegram identity/initData
  -> владелец создаёт и видит одну задачу
  -> Telegram и Mini App передают её в один существующий Core
  -> локальный Codex/runtime выполняет задачу
  -> один authoritative state хранит статус
  -> статус, результат и артефакт видны в Telegram/Mini App
```

Mini App не является новой платформой или вторым orchestrator. Он — безопасная
мобильная проекция существующих задач и один дополнительный trusted ingress.

## 3. Что входит

- exact owner authentication;
- Telegram text/voice ingress и Mini App natural-text ingress;
- один task identity и один authoritative state;
- текущая queue/worker/outbox model;
- существующий local Codex/runtime;
- safe task list/detail/event/result/artifact views;
- idempotency, tenant binding, effect authority, audit и recovery;
- короткий development workflow с candidate-bound assurance.

## 4. Что не входит

- второй Core, orchestrator, queue, state store, policy или effect engine;
- перенос всей authority на VPS;
- universal Agent Registry, peer-to-peer agents и agent marketplace;
- Web IDE, terminal, arbitrary shell, self-update и self-deploy;
- multi-user SaaS, billing, RBAC и tenant administration;
- обязательный document/Google/analytics platform;
- Gate 0–8 как Definition of Done текущего MVP-1;
- speculative framework/service/repository.

## 5. Trust и authority invariants

1. Core, а не LLM/client, назначает tenant, actor, route, risk, capability,
   state и effect.
2. LLM/worker не получает credentials и не исполняет внешний effect напрямую.
3. Telegram и Mini App используют одну task identity, queue/state model и
   effect authority.
4. Повтор ingress/approval/delivery безопасен; unknown provider effect не
   повторяется вслепую.
5. Task/result/artifact и approvals tenant/task/revision-bound.
6. Secrets, raw payload/audio, local path и данные другого tenant не входят в
   UI, logs, errors или evidence.
7. Runtime approvals определяются sealed docs 06/07 и могут быть строже
   development workflow.
8. TARGET становится CURRENT только после кода, проверок и exact Git binding.

## 6. Минимальный Mini App

Первый новый deployment unit — `Mini App Web Boundary`:

- static UI;
- public HTTPS ingress;
- bounded pass-through raw Telegram `initData` в Core;
- pass-through для Core-issued short-lived session;
- thin API adapter к существующему Core;
- безопасные task/result/artifact projections.

Boundary не хранит отдельную authoritative БД и не маршрутизирует/исполняет
задачи сам, не имеет bot secret и не выдаёт auth verdict/session.
Только Core проверяет signature/freshness/owner/replay и выпускает/
валидирует session. Boundary не кэширует raw `initData`, bearer или
auth verdict. При недоступном local Core он fail-closed.

Обязательные browser/API controls: exact bot/owner, signature,
`auth_date` freshness/future skew, replay generation, exact Origin/Host,
same-origin API, CSP, no wildcard CORS, body/time/rate bounds, in-memory opaque
bearer, sanitized errors и tenant/task-bound artifact delivery.

Mutating request id проходит end-to-end до Core и связывается с
owner/session/operation/request digest. Boundary не делает blind retry;
потерянный ACK разрешается readback/reconciliation по тому же request id.
ADR 0025 добавляет Core-owned recovery credential в HttpOnly cookie; старое
initData не переиспользуется и срок исходной Telegram подписи не продлевается.
Явная отмена возможна лишь для запроса, ещё отсутствующего в Core: durable
tombstone не даст запоздалому POST создать задачу. Уже записанный UNKNOWN
сохраняется до authoritative сверки.

## 7. Product runtime approvals и Codex workflow

Product/runtime `ApprovalRequest/ApprovalDecision` связывает конкретный
effect, owner, task, revision, target и expiry. ADR 0022 не ослабляет эту
политику.

Локальный process разработки:

`TASK -> WIP_ITERATION -> CHECKPOINT -> GATE_CANDIDATE -> MERGE -> RELEASE_PRODUCTION`.

Обычный WIP выполняет target L1. Полный independent L1/L2/L3 выполняется по
одной frozen coherent candidate revision. Formal quality-L4 нужен только для
удаления данных с ПК или критического изменения кабинета маркетплейса. Push,
deploy и другие внешние действия требуют отдельной явной авторизации по общей
безопасности.

## 8. Active closure-roadmap

**Один Gate = одна Codex-задача = один пользовательский чат.** Txx/Cxx и
прежние R01–R47 — внутренние checkpoints, не отдельные чаты.

1. C0 — единая истина и контракт.
2. C1 — универсальное семантическое понимание.
3. C2 — voice parity и ASR qualification.
4. C3 — стабильность Core/backend/worker.
5. C4 — завершённый frontend/user journey.
6. C5 — operations/recovery/security.
7. C6 — frozen release и owner acceptance.

Каждый следующий Gate начинается только в новом чате от принятого exact
result SHA/tree и handoff предыдущего. MVP-2 не начинается до PASS C6.

## 9. Источники истины

- Git хранит code, tests, ADR, CURRENT и permanent docs.
- GitHub `main`/release tag становится опубликованным каноном только после
  разрешённого merge/release и remote SHA readback.
- Nobus Memory хранит pointer/status/decision/freshness и не заменяет Git.
- Gate 0 evidence относится только к своей старой revision/digest.
- История текста находится в Git; длинные snapshots в активных docs не нужны.

## 10. Definition of Done MVP-1

MVP-1 готов, когда backend и frontend одного exact release воспроизводимо
проходят owner-bound сценарий из Telegram через Mini App, один Core, local
runtime и authoritative state обратно к status/result/real artifact; negative
auth/tenant/replay/idempotency/effect/restart/recovery cases проходят; release
активирован, имеет health/backup/restore/rollback/owner smoke, а remote SHA и
final tag прочитаны обратно. Локальный commit, static frontend source или
зелёный unit subset сами по себе не являются MVP verdict.

Multi-user platform, full Gate 2A и Gate 3–8 не являются prerequisite этого
вердикта.
