# ADR 0028 — Согласование остановки после гибридного выключения Windows

Дата: 20 сентября 2026 года. Статус: кандидат отдельного эксплуатационного исправления. Историческая приёмка MVP1 и M1-S1 от 19 сентября не изменяется; MVP2 не запускается.

## Причина

Вечером 19 сентября Windows завершила пользовательскую сессию при гибридном выключении, а утром 20 сентября возобновилась с тем же BootIdentifier. В подписанной истории остался `starting` без terminal. Принятое M1-S1 правило допускает автоматическое согласование только при ином BootIdentifier, поэтому первый запуск и повтор после backup остановились с кодом 78. Проверенный backup не мог отменить запрет истории. Дополнительно валидатор ошибочно относил истёкший Telegram callback `kind=action` к исполняемым внешним эффектам.

[Microsoft описывает](https://learn.microsoft.com/en-us/windows/win32/power/system-power-states) Fast Startup как выключение с сохранением ядра в hibernation file и завершением пользовательских сессий. На данном ПК локальный `HiberbootEnabled=1`; изменить его из доступной учётной записи не удалось, значение осталось прежним. Новый код учитывает такой переход без отключения системного режима.

## Новое узкое разрешение

Если signed history оканчивается `starting` с прежним BootIdentifier, автоматическое продолжение допустимо только при свежей связанной паре событий Windows System: `Kernel-Power/42` после времени подписанного `starting` и `Power-Troubleshooter/1` с согласованными `SleepTime` и `WakeTime`. События читаются в ограниченном количестве и только из штатных провайдеров System. Их порядок, RecordId и времена проверяются в UTC; wake должен быть не старше 15 минут. Отсутствие, неподходящая форма, повреждение, отказ чтения и изменение доказательства дают STOP. Доказательство проверяется повторно под блокировками перед записью.

Существующие исключающие блокировки supervisor/Core/backup, проверка отсутствия прежних детей и listener, четырёх БД, lease, задач, эффектов и доставок сохраняются. Новый подписанный `power_reconciled` в схеме истории v5 связывает digest прежнего `starting`, прежний и текущий одинаковые BootIdentifier и digest пары событий. Следующая попытка тратит прежний бюджет. После настоящей смены BootIdentifier продолжает применяться прежний `reboot_reconciled` v4. Здоровый работающий экземпляр нельзя согласовать как брошенный.

Для `telegram_capabilities.kind=action` отдельно проверяется защищённая Telegram-кнопка. Только истёкший callback владельца одной из четырёх действующих голосовых команд MVP1 считается инертным при совпадении token digest, payload digest, схемы и срока в записи. Действующий, неверно привязанный, неизвестный либо относящийся к расширенным действиям callback остаётся STOP. Исполняемые effect capabilities сохраняют прежнее правило: только проверенное `delivered` безопасно; pending/executing/completed/unknown требуют оператора.

## Совместимость и отказ

Старая версия не понимает v5 после появления `power_reconciled`; её нельзя запускать над такой историей без отдельного reader-патча. Новый `m1-s1-power-rollback-compat.patch` накладывается поверх исторического `m1-s1-rollback-compat.patch` только в изолированном rollback-кандидате. Он читает и проверяет v5, не обнуляет историю и позволяет exact rebind лишь после доказанного clean stop. Возврат БД из старой копии не является rollback. Оба патча хранятся с LF для `git apply` на Windows; синтетический fixture создаёт собственный Git-репозиторий, чтобы применение не было молча пропущено из-за родительского checkout.

Если события Windows не читаются, прошло более 15 минут после wake или любая проверка данных неоднозначна, действует прежний операторский STOP. Это осознанная граница доступности, а не основание удалить историю, выключить admission hold или ослабить binding.

## Доказательства кандидата

Синтетические тесты покрывают прежний и тот же BootIdentifier, однократность, привязку подписанной истории, stale/missing/reordered power events, изменение доказательства, присутствие runtime, неизвестный эффект, истёкший/действующий/чужой callback, чтение v5 rollback-ридером и точный rebind после clean stop. Штатный парсер read-only подтвердил форму реальной пары событий 19–20 сентября на историческом времени wake; новый реальный shutdown ради теста не выполнялся. Production-статус, точная версия и сохранность данных устанавливаются отдельно при развёртывании.
