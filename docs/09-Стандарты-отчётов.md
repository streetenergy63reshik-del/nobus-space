# 09. Стандарты отчётов

**Статус документа:** CANONICAL
**Состояние реализации:** CURRENT Telegram projection / TARGET report store v1
**Дата актуализации:** 24 июля 2026

## CURRENT и TARGET

**CURRENT:** отдельные генераторы `report.v1` и постоянное report store отсутствуют. Для Telegram реализована безопасная product projection из durable Task/outbox: verified answer либо короткий terminal failure без task/event/revision IDs. Handoff-файлы остаются материалами разработки, а не экземплярами схем v1.

**TARGET:** каждый результат хранится как versioned machine-readable отчёт с tenant/task binding, provenance, cost и evidence; Telegram показывает его безопасное краткое представление.

## 1. Общий envelope

Каждый отчёт v1 содержит поля следующего нормативного type profile. YAML ниже — читаемое описание типов, а не самостоятельная JSON Schema; до реализации генератора ему обязаны соответствовать Pydantic/JSON Schema и golden tests.

```yaml
schema: nobus.report.v1
report_type: task_result | approval_preview | daily_ops | incident | release | restore
report_id: uuid
scope: tenant | system
tenant_id: string | null
task_id: uuid | null
contract_digest: sha256 digest | null
result_revision: integer | null
result_digest: sha256 digest | null
verification_bundle_id: uuid | null
verification_bundle_digest: sha256 digest | null
approval_request_id: uuid | null
approval_decision_id: uuid | null
generated_at: UTC server timestamp
generator:
  component: string
  version: string
period:
  from: UTC timestamp | null
  to: UTC timestamp | null
sources:
  - id: string
    version_or_hash: string
verification:
  l1: PASS | FAIL
  l2: PASS | FAIL | PENDING
  l3: PASS | FAIL | PENDING
  l4: APPROVED | REJECTED | EXPIRED | PENDING | NOT_REQUIRED
versions:
  policy: string
  model: string | null
  prompt: string | null
  tools: {tool_id: version}
cost:
  amount: decimal | null
  currency_or_unit: string
limitations: [string]
```

Дополнительно каждый тип имеет свой `payload`. `tenant_id=null` допустим только при `scope=system`; такой отчёт доступен только платформенной роли, не смешивает клиентские payload и формирует отдельные tenant-safe проекции. Неизвестные обязательные данные не заполняются нулями: ставится `null` и объяснение в `limitations`. Денежные значения передаются decimal-строкой вместе с валютой, время — UTC с timezone.

Блок `verification` — удобная проекция связанных записей. Источниками истины остаются `VerificationBundle`, `ApprovalRequest` и `ApprovalDecision` по ID и digest; отчёт не может сам разрешить transition, внешний эффект или объявить L4 пройденным.

Отчёт не содержит secrets, tokens, cookies, лишние персональные данные и raw prompt. Tenant/task binding обязателен для всех клиентских результатов.

## 2. Краткий Telegram-формат

Product projection зависит от результата, а не повторяет технический audit:

- обычная текстовая задача: без отдельного «задача принята»; создаётся одна редактируемая карточка стадий/heartbeat, которая удаляется после финала;
- голос: бот показывает transcript и кнопки `Подтверждаю` / `Отмена`; использованная карточка удаляется, затем применяется общий progress-flow;
- progress содержит только безопасные операционные стадии и elapsed time, но не chain-of-thought, prompt, пути, IDs или raw errors;
- informational answer: только пользовательский ответ на языке задачи;
- code patch: только тогда появляется L4-flow — краткое описание, список файлов, полный diff и кнопки `Применить` / `Отклонить`;
- Task UUID, Event/Revision, digests, capability tokens, локальные пути, worker error details и служебные команды в обычном интерфейсе не показываются.

Telegram-сообщение не является источником истины. Полные bindings, verification evidence и receipts остаются в Core/SQLite audit; будущий длинный отчёт отдаётся отдельным файлом либо безопасной ссылкой с ограниченным сроком.

## 3. `task_result.v1`

Обязательный payload:

```yaml
request_summary: string
outcome: COMPLETED | FAILED | REJECTED | ESCALATE
deliverables:
  - name: string
    location: string
    media_type: string
    sha256: string
metrics:
  - name: string
    value: decimal | string
    unit: string | null
evidence:
  - level: L1 | L2 | L3
    verifier_id: string
    method: string
    location: string
    sha256: string
verification_bundle_id: uuid
verification_bundle_digest: sha256
next_actions: [string]
```

`COMPLETED` недопустим при `PENDING`/`FAIL` любого L1–L3. Ссылка без хэша не считается evidence для изменяемого артефакта.

## 4. `approval_preview.v1`

Этот отчёт формируется перед внешним действием и неизменяемо связывается с L4:

```yaml
request_id: uuid
contract_digest: sha256
result_revision: integer
result_digest: sha256
action_type: string
tool_id: string
target:
  display: string
  stable_id: string
changes:
  - field_or_object: string
    before: string | null
    after: string | null
money:
  amount: decimal | null
  currency: string | null
consequences: [string]
rollback: string | null
action_digest: sha256
idempotency_key: string
requested_at: UTC server timestamp
expires_at: UTC server timestamp
```

Кнопки: `Подтвердить` и `Отклонить`. Молчание или истечение TTL означает: действие не выполнено, approval закрыт как `approval_expired`, для повтора требуется новый preview. Никаких значений «по умолчанию согласен» нет.

Для `approval_preview.v1` поля envelope `approval_request_id`, `contract_digest`, `result_revision` и `result_digest` равны соответствующим полям payload (`request_id` и одноимённые bindings), а `approval_decision_id` остаётся `null` до явного решения.

## 5. `daily_ops.v1`

Обязательный payload:

```yaml
tasks:
  created: integer
  completed: integer
  failed: integer
  escalated: integer
  waiting_human: integer
quality:
  l1_failures: integer
  l2_disagreements: integer
  l3_findings: integer
external_actions:
  proposed: integer
  approved: integer
  executed: integer
  rejected_or_expired: integer
  unknown_outcome: integer
operations:
  oldest_queue_age_seconds: integer
  incidents_by_severity: {SEV-1: integer, SEV-2: integer, SEV-3: integer, SEV-4: integer}
  backup_age_seconds: integer | null
  last_restore_drill: UTC timestamp | null
cost_by_provider: {provider: decimal}
```

Если метрика ещё не собирается, она `null`, а не выдуманная цифра. Daily report агрегирует один tenant; cross-tenant отчёт доступен только системной роли и не раскрывает клиентские детали.

## 6. `incident.v1`

Обязательный payload:

```yaml
severity: SEV-1 | SEV-2 | SEV-3 | SEV-4
status: OPEN | CONTAINED | RESOLVED | CLOSED
detected_at: UTC server timestamp
contained_at: UTC server timestamp | null
resolved_at: UTC server timestamp | null
detected_by: string
affected_tenants: [opaque tenant id]
affected_components: [string]
impact: string
timeline:
  - at: UTC server timestamp
    actor: string
    event: string
containment: [string]
data_exposure: CONFIRMED | SUSPECTED | NONE | UNKNOWN
external_actions: [receipt id]
root_cause: string | null
prevention: [string]
regression_evidence: [location + sha256]
```

До подтверждения facts помечаются `UNKNOWN`/`SUSPECTED`. Incident report не содержит raw secrets или клиентские payload. Закрытие требует root cause, prevention и regression evidence.

## 7. `release.v1`

Обязательный payload:

```yaml
environment: development | staging | production
commit: git sha
artifact_digest: sha256
schema_version: string
changes: [string]
migrations: [id]
configuration_revision: sha256
deployment_action_digest: sha256
known_risks: [string]
rollback_plan: string
test_evidence: [location + sha256]
security_review: PASS | FAIL | PENDING
deployed_at: UTC server timestamp | null
deployment_receipt: string | null
```

`deployment_action_digest` покрывает environment, artifact, migrations, configuration revision и rollout scope. `git push` не заполняет `deployed_at`: deployment подтверждается receipt среды. Для production поля envelope `approval_request_id` и `approval_decision_id` обязательны, Decision имеет `approved`, а `ApprovalRequest.action_digest` совпадает с `deployment_action_digest`.

## 8. `restore.v1`

Обязательный payload:

```yaml
backup_id: string
backup_created_at: UTC server timestamp
manifest_digest: sha256
encryption_verified: boolean
restore_started_at: UTC server timestamp
restore_finished_at: UTC server timestamp | null
environment: isolated-test | staging | production
components: [string]
integrity_checks: [name + verdict + evidence]
tenant_isolation_check: PASS | FAIL
observed_rpo_seconds: integer | null
observed_rto_seconds: integer | null
data_loss_or_gaps: [string]
verifier_id: string
```

Restore не объявляется успешным без integrity и tenant-isolation checks. Расхождения фиксируются явно; формулировка «без потерь» допустима только при наличии измеримого доказательства.

## 9. Версионирование

- Добавление необязательного поля совместимо внутри `v1`.
- Удаление, переименование или изменение семантики поля требует `v2`.
- Генератор хранит точную schema version вместе с отчётом.
- Prompt/model/tool/policy versions и cost являются evidence, а не декоративными metadata.
- Шаблон меняется через ADR или документированное решение, тест совместимости и L1–L3; production-применение требует L4.

Правила проверок определены в `06-Регламент-качества-L1-L4.md`, внешних действий — в `07-Правила-внешней-записи.md`, эксплуатации — в `08-Runbook-эксплуатации.md`.
## Telegram product answer

Итог владельцу содержит только полезный результат: короткий заголовок при
необходимости, абзацы, списки и проверяемые ссылки для web research. Не выводятся
UUID задач, revision/event IDs, capability, локальные абсолютные пути, chain of
thought и сообщения «файлы пока не меняются». Progress — одна обновляемая карточка;
после терминального результата она удаляется. Ошибка сообщает безопасную причину
и следующий практический шаг без внутренних деталей.
