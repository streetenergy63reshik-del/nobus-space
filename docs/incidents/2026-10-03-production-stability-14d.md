Период: с 20.09.2026 00:00 МСК до проверки 03.10.2026 около 12:04 МСК. Источник — фактический LIVE `bd991760312732dd15cdad909e81a6023cc703f2`, установленные аргументы трёх заданий, подлинная DPAPI-аутентифицированная recovery history, штатная диагностика и прежние записи инцидентов. Это число попыток, а не число независимых первопричин или интервалов полного простоя.

Наблюдения и связанные digests сохранены в [обезличенном доказательстве](System/2026-10-03-stability-evidence.json). Проверено 23 370 подлинных диагностических записей. Проверки отсортированы по времени; для terminal взяты только предыдущие проверки того же run/attempt за три минуты. Журнал содержит категории и агрегаты, без сообщений, содержимого БД и сырого stderr SSH. Первопричину, которой нет в доказательствах, считаем UNKNOWN.

## Подтверждённые дефекты и мероприятия

1. **Распознавание SSH.** В `bd99176` классификатор не распознавал стандартные сообщения OpenSSH `client_loop: send disconnect: Broken pipe`, keepalive timeout и EOF установленного транспорта. Это воспроизведено на синтетических примерах из [исходника OpenSSH 9.5](https://raw.githubusercontent.com/openssh/openssh-portable/V_9_5_P1/clientloop.c). Такой сбой получал UNKNOWN и STOP. Исторические exit 255 могли быть вызваны другим событием: сырой stderr не сохранён, поэтому их причины остаются UNKNOWN.
   Исправление: строгие полные шаблоны одного сообщения либо конкретной пары read/disconnect; только существующие категории транспорта. Неполный/слишком большой поток, неизвестный banner, конфликт, ключ, authentication, host verification и configuration сохраняют STOP. Retry по-прежнему только после доказанного cleanup, максимум 10 раз с паузой 60 с; второй Core/relay не создаётся. Host verification, отдельный known_hosts и существующий keepalive 20/3 сохраняются. Для фонового SSH явно задан `StdinNull=yes`; уровень логирования не понижается, чтобы не скрыть keepalive timeout.
2. **Занятая SQLite в цикле Core.** Безопасная запись стеков выявила синхронные queue claim/commit, voice purge и checkpoint release на потоке Core. 02.10 около сбоя были задержки 1,5–3,1 с в SQLite и отдельный read `desktop_bridge_state.list_requests`. Они объясняют возможность задержки endpoint, но не доказывают точную причину измерения 95 с. Пары suspend/resume в этот интервал нет.
   Исправление: idle claim, health queue snapshot, polling checkpoint и периодический bridge list выполняются вне event loop. Каждая транзакция остаётся цельной, со своей SQLite connection. Отмена ждёт commit/rollback; поздно полученный job/polling lease освобождается точно владельцем. Guarded execution/effect transactions, сроки voice cleanup, tenant isolation, idempotency, delivery и schema не ослабляются. Проверяются реальный SQLite lock, повторная отмена и порядок commit → release.
3. **Backup и binding.** Закрепить в runbook порядок: inspect stopped state/effects → exact ack при необходимости → Backup Enabled/Ready → единственный разрешённый startup/цикл. Не повторять unknown/in-progress backup. Новый code binding выпускается только после regression, сохранения exact XML/config/launcher/HEAD, hold, штатного STOP, доказательства отсутствия дерева/lease/listener, staged disabled Backup, точного rebind и одного reconcile от прежней complete-квитанции.
4. **Питание и наблюдение.** Не выдавать Kernel-Power 41 за аппаратный диагноз. Сохраняются автозапуск после входа пользователя, штатная проверка fresh boot/power proof, fail-closed при неизвестных эффектах и контроль в 08:00/22:00 МСК. Сбой питания ПК и длительная недоступность сервера требуют отдельной диагностики по новому событию; код не может гарантировать работу выключенного компьютера. Исторические UNKNOWN не являются основанием ослабить binding или очистить историю.

На этапе подготовки: 278 связанных тестов PASS; затем 50 проверок новых failure paths и runner PASS. Это проверки WIP, не допуск к выпуску.
