# 10. Политика памяти и данных

**Статус документа:** CANONICAL
**Состояние реализации:** CURRENT для локального owner-runtime; multi-tenant production persistence/retention остаются TARGET
**Дата актуализации:** 25 июля 2026

## 1. Принципы

1. Память не равна источнику истины: состояние задачи подтверждается транзакционным Core, артефакты — хэшами, внешние действия — receipts.
2. Данные каждого tenant логически и физически изолируются настолько, насколько позволяет выбранное хранилище. Cross-tenant retrieval запрещён по умолчанию.
3. Система хранит минимум данных на минимально необходимый срок.
4. Секреты не записываются в prompt, Markdown, Git, логи, отчёты или learning memory.
5. Данные не становятся обучающим материалом автоматически. Для promotion нужны обезличивание, L1–L3 и одобрение человека.
6. Backup не продлевает законный retention и не отменяет запрос на удаление.

## 2. CURRENT и TARGET

### CURRENT

- Task queue, confirmations, progress, outbox и Business Notes локально сохраняются в canonical SQLite runtime и восстанавливаются после restart. Raw worker context остаётся bounded и не становится долговременной памятью автоматически.
- `.nobus-quality` содержит локальные обезличенные записи процесса разработки.
- Локальный SQLite runtime имеет tenant-scoped snapshots/events/outbox и fail-closed restart semantics, но retention jobs, legal hold, production audit store и процедура offboarding отсутствуют.
- Клиентские production-данные использовать нельзя. Owner-only «Заметки бизнеса» являются отдельным локальным CONFIDENTIAL-контуром: payload защищён DPAPI, выборка строго tenant/chat/topic-scoped, содержимое не передаётся внешней LLM.

### TARGET

- транзакционная база для задач, событий, approvals и audit metadata;
- объектное/файловое хранилище для артефактов с tenant-scoped access и hashes;
- отдельная ephemeral workspace для worker;
- secret store для credentials;
- отдельная project/learning memory только из проверенных и обезличенных материалов.

## 3. Классы данных

| Класс | Примеры | Минимальная защита |
|---|---|---|
| `PUBLIC` | опубликованный материал | integrity, provenance |
| `INTERNAL` | архитектурные документы, обезличенные метрики | access control, backup |
| `CONFIDENTIAL` | клиентские отчёты, договорные данные, prompts с бизнес-контекстом | tenant isolation, encryption, audit |
| `SECRET` | credentials, платежные/идентификационные данные, access tokens | только secret store/специализированное хранилище, строгие роли; запрещено в contract, prompt, result, evidence и LLM context |

При сомнении применяется более строгий класс. Владелец данных и законное основание фиксируются при onboarding; без них сохранение production-данных блокируется.

## 4. Виды памяти

### 4.1. Ephemeral worker memory

Содержит только входы и промежуточные файлы конкретной задачи. Доступ ограничен `tenant_id` и `task_id`; сеть, инструменты и файловые пути выдаются allowlist. После завершения/отмены workspace очищается, а факт очистки записывается без содержимого.

### 4.2. Task и audit memory

Хранит TaskContract, state transitions, result revisions, VerificationBundle, HumanApprovalRecord и внешние receipts. Записи append-only либо versioned; терминальные события не перезаписываются.

### 4.3. Project knowledge

Содержит утверждённые ADR, инструкции, схемы и активные уроки проекта. Изменения версионируются, имеют автора и основание. LLM не переписывает политику автоматически.

### 4.4. Learning memory

Case record обезличивается и не содержит tenant secrets или персональные клиентские данные. Ошибка становится уроком только после root cause, prevention, regression check и человеческого approval. Успешный случай становится golden case только после независимого воспроизведения и approval.

### 4.5. Secrets

Секреты не являются памятью агента. Worker получает краткоживущую capability либо adapter использует secret непосредственно. Любое чтение/ротация/отзыв аудируются.

### 4.6. Nobus Memory

`C:\Хранилище\АГЕНТ\Nobus memory` — курируемый Obsidian graph с provenance,
а не копия source systems. Telegram runtime использует trusted server-side
progressive retrieval: до семи релевантных Markdown notes, общий лимит 14 000
символов, обязательные scope/status/updated/source и исключение неупомянутых
client contours. `.git`, `.obsidian`, Sources, Archive, Templates и
secret-like notes модели не передаются.

Memory block считается данными, а не инструкциями, и не расширяет tools или
filesystem authority Codex CLI. Точная команда владельца `Сохрани в Nobus
Memory: <текст>` создаёт отдельную атомарную запись `pending_review` в
`01 Inbox`; существующие решения, project/client notes, skills и policies бот
не переписывает. Promotion выполняется только после source-check, L1/L2/L3 и
необходимого human approval. Текущие Calendar/Tasks/Drive всегда обновляются
через Google API, а не из сохранённого snapshot.
## 5. Tenant isolation и доступ

- Tenant определяется доверенной границей, а не текстом запроса или LLM.
- Каждый запрос к базе/объекту требует tenant predicate; отсутствие tenant — ошибка.
- Cache, vector index, logs, backup manifest и search также tenant-scoped.
- Сервисные роли имеют минимальные права; support-доступ временный, обоснованный и аудируемый.
- Перед выдачей пользователю объект повторно проверяется на tenant/task binding.
- Тесты включают cross-tenant IDs, одинаковые имена файлов, cache poisoning и retrieval leakage.

## 6. Retention

Ниже — **целевые начальные значения**, которые должны быть подтверждены владельцем и правовой/договорной проверкой до production. Контракт tenant или закон может требовать более короткий или длинный срок.

| Данные | Целевой срок по умолчанию |
|---|---|
| временные worker-файлы | удалить после задачи, но не позднее 24 часов |
| raw voice | удалить после подтверждения транскрипта, но не позднее 1 часа; при отказе — сразу |
| технические логи без payload | 90 дней |
| TaskContract, результаты и VerificationBundle | 365 дней |
| approvals, audit events, external receipts | 730 дней |
| incident records | 730 дней после закрытия |
| проектные ADR и утверждённые уроки | срок жизни проекта + 365 дней |
| клиентские исходные данные | только по договору; без заданного срока onboarding блокируется |

Legal hold приостанавливает удаление только для точно определённых объектов, имеет основание, владельца, срок пересмотра и audit event. «Хранить всё на всякий случай» запрещено.

## 7. Удаление

1. Проверить identity, tenant, основание и scope запроса.
2. Сформировать manifest данных и preview последствий.
3. Получить L1–L3 и L4, потому что удаление — внешнее необратимое действие.
4. Заблокировать новое использование объектов и выполнить idempotent deletion.
5. Удалить индексы, caches, производные артефакты и ссылки.
6. Зарегистрировать tombstone/receipt без удалённого содержимого.
7. Дождаться естественного истечения зашифрованных backup либо применить утверждённое crypto-erasure; срок сообщить владельцу данных.
8. Независимо проверить отсутствие доступных копий и cross-links.

Неудачное или частичное удаление получает `ESCALATE`; система не сообщает «удалено», пока проверка не завершена.

## 8. Offboarding tenant или сотрудника

### Tenant

- получить action-bound L4 на manifest операций offboarding;
- остановить новые задачи и внешние действия;
- отозвать integrations, tokens и service identities;
- предоставить утверждённый экспорт с manifest/hashes, если это предусмотрено договором;
- удалить либо передать данные по договорной процедуре;
- проверить caches, indexes, backups и shared locations;
- сохранить только обязательный audit минимум на разрешённый срок;
- выдать deletion/export receipt.

### Пользователь или сотрудник

- получить action-bound L4 на отзыв прав и ротацию credentials;
- немедленно отозвать sessions, credentials и роли;
- передать owned approvals/tasks уполномоченному лицу;
- ротировать общие секреты, если они могли быть доступны;
- проверить административные действия и необычные выгрузки;
- не удалять audit events, относящиеся к безопасности.

## 9. Неизменяемый audit trail

Audit event содержит:

- event ID, server timestamp и sequence;
- actor/service identity, auth method и role;
- tenant, task, `contract_digest`, `result_revision`, `result_digest` и event type;
- source/request ID и idempotency key;
- before/after hashes либо action digest без secret payload;
- policy, schema, model, prompt и tool versions;
- cost, verdict, error category и external receipt;
- retention class и legal-hold marker.

Audit events append-only, криптографически связаны или защищены эквивалентным механизмом целостности, реплицируются отдельно и доступны по принципу наименьших прав. Исполнитель и LLM не могут удалить или переписать их.

## 10. Provenance и стоимость

Для LLM/tool результата сохраняются:

- provider, точная model/tool version;
- prompt template version и policy version;
- хэши разрешённых входов и результата;
- token/request usage, стоимость и валюта/единица;
- cache status и retry count;
- verifier identities и evidence locations.

Raw prompt сохраняется только если это необходимо и разрешено классом данных; предпочтителен безопасный hash плюс структурированное provenance. Изменение версии не считается эквивалентным результатом без новой проверки.

## 11. Backup и память

Backup шифруется, tenant manifests сохраняются отдельно, restore проверяет tenant isolation. Retention job знает о backup generations и подтверждает, когда удалённые данные перестали быть восстановимыми. RPO/RTO и процесс restore задаются в `08-Runbook-эксплуатации.md`; до их утверждения production запрещён.

Контроль качества памяти описан в `06-Регламент-качества-L1-L4.md`, внешнее удаление и изменение — в `07-Правила-внешней-записи.md`, форматы audit/restore — в `09-Стандарты-отчётов.md`.
## Product context and Business Notes

- `docs/11-Контекст-продукта.md` — короткий санитизированный контекст, а не
  замена бизнес-памяти; он добавляется только к релевантным вопросам.
- «Заметки бизнеса» индексируются локально, шифруются DPAPI и изолируются по
  tenant/chat/topic. Личные резюме агрегируют только привязанные темы владельца.
- Raw Business Notes не отправляются внешней LLM в MVP-1; резюме и извлечение
  задач выполняются локально.
- Контекст явно выбранного файла эфемерен в worker contract/outbox flow, bounded,
  digest-bound и не становится долговременной памятью автоматически.
