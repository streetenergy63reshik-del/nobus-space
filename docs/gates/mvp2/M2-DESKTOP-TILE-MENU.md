## Пользовательский путь

1. Участник закрытой группы «Заметки бизнеса» нажимает постоянную кнопку
   `/codex@Nobusspacebot` под полем ввода в теме «Codex work». Она отправляет
   ту же команду; при скрытой клавиатуре её можно раскрыть значком у поля.
   Запасной вход — выбрать `/codex` в меню команд бота либо отправить
   `/codex@Nobusspacebot` вручную. Бот проверяет живой IPC
   установленного Codex Desktop на ПК. Если соединения нет, отвечает:
   «Codex не активен на ПК. Откройте Codex Desktop»; меню не открывается.
2. Бот показывает плитки **актуальных локальных проектов Codex**. В каждой
   карточке до шести проектов, две плитки в строке. Есть переход между
   страницами и «Назад»; на первой ступени «Назад» закрывает меню.
3. При выборе проекта бот повторяет проверку Desktop и перечитывает каталог.
   Открывается список задач именно этого проекта: «Новая задача» и текущие
   незархивированные задачи. По шесть существующих задач на страницу, с
   кнопками страниц и «Назад» к проектам. Название задачи — отображаемое имя
   Codex; для исполнения используется точный thread ID.
4. Выбор существующей или новой задачи снова проверяет Desktop и перечитывает
   каталог. Бот показывает выбранные проект и задачу, оставляет «Назад» к
   задачам и отправляет автору `ForceReply` с пустым полем ввода. Текст нужно
   отправить ответом на эту карточку. Кнопка не добавляет текст промта.
5. После ответа бот ещё раз проверяет Desktop и выбранные ID в свежем
   каталоге, принимает не более 12 000 символов и один раз передаёт исходный
   текст в существующий `DesktopBridgeService`. При выборе «Новая задача»
   bridge создаёт задачу через проверенный UIA bootstrap; для существующей
   задачи продолжает точный thread через owner IPC. Квитанция о принятии и
   полный результат приходят в исходную тему по прежнему механизму M2.
   После доставки бот удаляет свои временные карточки меню, `ForceReply`,
   квитанцию о приёме и сообщения о ходе задачи; итоговый текст и вложения
   остаются. Сообщения автора бот не удаляет.

Каждая кнопка меню Codex и каждое сообщение с выбором агента повторно
проверяет доступность IPC. Старое меню не является снимком, по которому можно
отправить задачу после изменения проекта/списка задач. Если проект или задача
исчезли, бот просит открыть `/codex` заново. Смена версии приватного IPC
отображается отдельной ошибкой несовместимости, а не как выключенный ПК.

## Источники и границы доверия

Telegram ingress проходит существующий `gateway.py`: доверие основано на
фактических numeric `user_id`, отрицательном group `chat_id`, tenant и теме.
Пересланное, анонимное или чужое нажатие не выбирает цель. Меню принадлежит
одному автору и одной теме; срок жизни — 30 минут. Callback содержит только
случайный UUID меню, номер его ревизии и индекс пункта. Сервер сверяет их с
локальной SQLite; старые кнопки после перехода становятся недействительными.
Общий Telegram gateway до маршрутизации сверяет токен плитки с живым меню,
его ревизией и точной парой numeric `user_id`/`chat_id`; прежние токены других
функций проходят свой отдельный реестр. Если Desktop временно недоступен,
ревизия меню не меняется и повторное нажатие даёт ту же ошибку доступности.
Текст промта в меню не хранится. Маппинг пунктов в SQLite кодируется тем же
DPAPI-кодеком, что и состояние bridge. Отдельная таблица хранит ID карточек
`ForceReply`, чтобы ответ на устаревшую карточку не стал новой задачей.

У проверенного Desktop IPC `\\.\pipe\codex-ipc` в текущем профиле нет
`list_projects` и `list_threads`. Для **показа** меню адаптер заново читает
собственный локальный индекс установленного Codex:

- `~/.codex/.codex-global-state.json`: порядок и записи `local-projects`,
  единственный `rootPaths`, привязки `thread-project-assignments` и host ID;
- `~/.codex/state_5.sqlite`, строго `mode=ro`: ID, отображаемое имя,
  свежесть, `thread_source`, `agent_path` и архивный флаг задач.

Формат приватный: адаптер ограничивает размер/форму, не кэширует снимок между
переходами и останавливается при несовместимой схеме. Облачные ChatGPT-проекты,
архив, subagent/guardian-задачи и задачи другого host в плитки не попадают.
Корни локальных проектов должны физически существовать, не содержать reparse
перехода и оставаться внутри owner workspace. Локальный
`desktop-projects.local.json` по-прежнему нужен для старого текстового входа
и проверки запуска; при плиточном выборе bridge обновляет разрешённый набор
из фактического каталога Desktop.

Индекс служит **списком кандидатов**, а не полномочием писать в задачу.
Непосредственно перед ходом действующий bridge находит Desktop owner точного
thread ID и через полную IPC-историю сверяет `cwd` с выбранным проектом.
Выгруженная задача открывается UIA по точному ID/сохранённому отображаемому
заголовку только для восстановления owner; после открытия IPC проверяет исходный
ID заново. При расхождении, нескольких кандидатах или потерянном ACK ход не
повторяется без readback. Создание проверяет видимый проект, пустой composer и
коррелирует bootstrap turn по маркеру. Очередь, сериализация, approvals,
вопросы, доставка файлов и аудит остаются у существующего Desktop bridge.

## Агенты в группе

Артур Nobus, Артур младший и Альберт входят тем же доверенным group ingress по
своим реальным Telegram numeric ID. Роль/отображаемое имя не дают отдельного
права и не подменяют ID. Telegram Bot-to-Bot Communication доставляет прямые
ответы бота на сообщение другого бота; обычный Bot API не предоставляет ботам
метод нажатия inline-кнопки ([Bot-to-Bot Communication](https://core.telegram.org/api/bots/bot-to-bot),
[кнопки Telegram](https://core.telegram.org/api/bots/buttons)). Поэтому карточка также нумерует те же пункты:
агент отвечает номером на **текущую** карточку, затем отвечает промтом на
точную `ForceReply` карточку. Это та же серверная машина состояний и те же
проверки, что при нажатии плиток человеком. Для bot-to-bot сообщений действует
уже установленный лимит четырёх новых запросов за десять минут и обычная
защита от циклов. Дополнительно ограничены четыре открытия меню за десять
минут и 32 перехода на одно меню. Разрешения Codex остаются адресованы владельцу.

## Ошибки, повтор и эксплуатация

- IPC отсутствует/не отвечает за три секунды: «Codex не активен…»;
  действие меню не применяется. Когда ПК снова доступен, пользователь
  открывает `/codex` и получает новые списки.
- Если выключен сам ПК, на котором одновременно работает бот, Telegram
  не может получить немедленный ответ от этого бота. После восстановления
  ПК требуется новая команда; мгновенная ошибка при полном выключении ПК
  потребовала бы отдельного постоянно работающего внешнего Telegram-контура.
- Каталог повреждён или изменил формат: список не угадывается, отправка
  блокируется до адаптации и проверки версии. Секреты и сырые файлы каталога
  не попадают в Telegram и журнал.
- Нажатие чужим ID, другой темой, по истечении 30 минут или старой ревизией:
  отказ без постановки задачи. Просроченный ввод промта также не исполняется.
- Неизвестный ACK Telegram при создании/правке карточки не вызывает слепую
  вторую отправку. Меню может стать устаревшим; безопасный выход — новое
  `/codex`.
- После принятия промта ingress key и bridge state обеспечивают one-shot;
  при lost ACK Desktop применяется прежний readback по `clientUserMessageId`.
- Разовый сбой IPC после принятия запроса переводит его в `waiting_pc` и
  запускает восстановление, но сам по себе не доказывает выключенный Desktop.
  Поэтому бот не отправляет немедленное сообщение «Codex Desktop недоступен».
  Отказ при нажатии кнопки до приёма промта остаётся явным.
- ID временных сообщений бота привязаны к точному bridge request в
  зашифрованном SQLite-состоянии. После `delivered` или `delivery_partial`
  удаление повторяется по этим ID, в том числе после рестарта; ошибки Telegram
  оставляют ID для следующей попытки. Исходный промт пользователя, итоговый
  ответ и файлы не входят в список очистки. При неуспехе/неизвестном исходе
  диагностическая карточка сохраняется. Ограничение Telegram на срок удаления
  сообщений может помешать очистке очень долгой задачи.

Кнопка `/codex` добавлена в Telegram bot commands: профиль применён 5 октября
и команда прочитана обратно из Telegram. В тему «Codex work» отправлено
сообщение № 3024 с постоянной Telegram reply keyboard, содержащей
`/codex@Nobusspacebot`; Bot API подтвердил chat/topic/message ID. Это
публикация входа, а не доказательство того, что конкретный клиент показал
клавиатуру или что нажатие прошло. LIVE переведён на `9aeff52` по плану
релиза M2. Тесты D02–D17 остаются за владельцем.

## Проверка этого изменения

Адресные тесты: свежий каталог и переименование, точная привязка выбранной
задачи, новая задача, кнопки «Назад» на всех ступенях, устаревший промт,
другой участник, выключенный IPC, bot-to-bot выбор по номеру, приоритет
маршрута callback, допуск плитки через общий gateway и Telegram payload
двухколоночных плиток/`ForceReply`.
Проверка локального индекса 04.10 показала 11 локальных проектов и 11 задач
Nobus Space; число задач Nobus Space совпало с `list_threads` Codex на тот же
момент. Это read-only сверка списка, не сквозная Telegram-приёмка.
