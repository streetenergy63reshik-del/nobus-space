# ADR-0006. Доступ к сервисам без официального API

**Статус решения:** PROPOSED
**Дата:** 20 июля 2026

## Контекст

Некоторые источники и кабинеты могут не иметь подходящего официального API. Браузерная автоматизация, сторонние прокси и обработка пользовательской сессии создают правовые, договорные, security и operational риски. Стабильность селекторов не решает вопрос допустимости доступа.

## Предлагаемое решение

1. Предпочитать официальный API, выгрузку, webhook или партнёрскую интеграцию.
2. Браузерный adapter рассматривать только после проверки Terms of Service, договора, прав на данные, применимого права и письменного решения владельца.
3. Не использовать residential proxy, маскировку fingerprint, CAPTCHA bypass, обход rate limits, блокировок, географических или access controls.
4. Если автоматизация разрешена, использовать отдельную service identity, минимальные права, allowlist доменов/действий, rate limits, MFA-compatible процедуру и полный audit.
5. Любая запись через browser adapter проходит L1–L3 и action-bound L4 по `../07-Правила-внешней-записи.md`.
6. Credentials остаются в secret store и не передаются LLM; содержимое страницы считается недоверенными данными и не может менять инструкции Core.

## Критерии перехода в ACCEPTED

- юридическая и договорная допустимость подтверждена для конкретного сервиса и tenant;
- выбранная интеграция не обходит защитные механизмы сервиса;
- есть threat model, owner, kill switch, monitoring и incident procedure;
- fake/staging adapter прошёл replay, prompt-injection, tenant-isolation и unknown-outcome tests;
- определены расходы, ограничения и план прекращения интеграции.

## Последствия

До принятия ADR такой adapter не допускается к production и реальным credentials. Отсутствие официального API может означать, что функция не реализуется; это допустимый и безопасный результат.
