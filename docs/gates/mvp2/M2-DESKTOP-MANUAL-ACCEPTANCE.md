## Как пользоваться

1. Откройте «Заметки бизнеса» → «Codex work» и настоящий Codex Desktop.
2. Для испытаний используйте только новые безвредные поручения и специально созданные файлы. Реальные клиентские документы, ключи и пароли не нужны.
3. Выберите один RUN, например UAT-20260927-01. При новом независимом прогоне замените суффикс. В примерах ниже заменяйте RUN своим значением, а THREAD — реальным ID задачи; слова RUN/THREAD не должны уходить буквально.
4. Команда и её задание — **одно сообщение**: первая строка /codex…, затем перевод строки и текст. Основной маршрут:
   ```text
   /codex@Nobusspacebot new nobus-orchestrator-dev
   Здесь текст задачи с уникальной меткой RUN-Dxx.
   ```
5. Ответ на вопрос/разрешение отправляйте через Telegram «Ответить» именно на последнюю карточку этого вопроса. Сообщение рядом в теме не считается привязанным ответом.
6. Если ответа нет, не отправляйте команду повторно. По истечении согласованного времени проверки сначала посмотрите Desktop, затем передайте разработчику время и ссылку на исходное сообщение. Он проверяет исход по IDs. Ни тестовая метка, ни одинаковый текст сами по себе не являются ключом повторной доставки.
7. PASS — выполнены все подпункты критерия; PARTIAL — выполнена часть; FAIL — наблюдаемое нарушение; BLOCKED — нет нужного участника/тестового средства; NOT_RUN — не проводили. BLOCKED и PARTIAL не превращаются в PASS.
8. После исправления повторять только затронутые подпункты с новой меткой, если это новое поручение. Не повторять старый неизвестный эффект.

## D07 — структурированные разрешения только владельцу

**Подготовка разработчика:** два настоящих Desktop requestApproval для безвредных тестовых операций, с обычным owner-reviewer. Нельзя заменить их простым текстовым вопросом или выключить глобальные ограничения. Первый пример эффекта — вывод уникального маркера командой; второй — создание нового тестового файла, который должен отсутствовать при deny. Точные команды и пути предъявляются в карточках.

1. Пусть Артур инициирует согласованный approval-сценарий. Карточка должна прийти в исходную тему с mention вашего owner-аккаунта, полным действием и целью.
2. Артур пробует ответить «разрешаю». Операция не выполняется.
3. Вы отвечаете reply «разрешаю». Проверьте в Desktop решение accept и реальный ровно один безопасный эффект.
4. На втором новом approval ответьте «отказать». Проверьте decline и отсутствие запрещённого эффекта/файла.
5. Повторите reply на уже закрытую карточку. Повторного исполнения быть не должно.
6. Пересланное сообщение с вашим именем или вашим прошлым «разрешаю» не должно разрешать новый запрос. Это проверяется с новым безопасным pending, затем вы его отклоняете.

**PASS:** numeric owner, точный pending request и действие совпадают; чужой/forward/replay не даёт разрешения.<br>
**FAIL:** accept до вашего ответа, работа по display name, действие после deny.<br>
**Сохранить:** полный текст двух карточек, ответы, request IDs и техническая квитанция accept/decline. Если реальный approval не возник — NOT_RUN, не PASS.

## D08 — сложные взаимодействия: неоднозначность, expiry, reconnect, гонка

Пять подпунктов обязательны. Разработчик готовит точные тестовые средства; вы запускаете их по одному и сверяете результат. Настройки времени production не менять.

1. **Неоднозначный requestUserInput.** Реальный вопрос «Можно отправить тестовый файл?» без доверенного структурированного approval должен направить владельца к ручной проверке в Desktop. Обычное Telegram «да» участника не разрешает действие. Это согласованное исключение, не общий запрет обычных вопросов.
