# 03. Архитектурный обзор Nobus Space

**Статус документа:** CANONICAL
**Архитектурный стиль:** deterministic Core, thin boundaries, replaceable workers
**Актуально на:** 25 августа 2026 года

Активный overlay:
[ADR 0022](adr/0022-thin-miniapp-orchestrator-mvp1-and-delivery-workflow.md).
Полный распределённый Gate 2A — **FROZEN / NOT CURRENT**.

## 1. Архитектурный вердикт

MVP-1 не создаёт новую distributed platform. Telegram chat и тонкий Telegram
Mini App используют существующий локальный Nobus Core, одну durable queue/state
model и одну effect authority.

```text
Telegram chat ------------------------------+
                                             |
Telegram Mini App -> Mini App Web Boundary --+-> existing local Nobus Core
                                                    |-> authoritative state
                                                    |-> local Codex/runtime
                                                    |-> application effects
                                                    `-> Telegram/Mini App delivery
```

## 2. CURRENT / TARGET

### CURRENT

- owner-bound Telegram ingress и local runtime присутствуют в exact Git base;
- Core/application boundary владеет task routing и effects;
- local Codex/runtime, durable queue/state/outbox и recovery primitives
  переиспользуются;
- точное live состояние процессов/провайдеров в этой docs-задаче не
  квалифицировалось;
- dirty Gate 1 WIP изолирован и имеет `HOLD / NOT_ACCEPTED`.

### TARGET ближайших slices

- `Mini App Web Boundary`;
- owner authentication;
- read-only task list/detail;
- natural-text create в existing Core;
- общие status/result/artifact projections;
- минимальные runtime approvals/recovery для фактически добавленных effects.

Linux Core migration, universal Agent Registry, Windows Development Worker
platform, Document Bridge platform и Gate 3–8 не являются active MVP topology.

## 3. Компоненты и authority

| Компонент | Ответственность | Не имеет права |
|---|---|---|
| Telegram ingress | parse, exact owner/chat binding, replay guard | назначать task authority из текста |
| Mini App Web Boundary | HTTPS, static UI, request bounds, unchanged pass-through, safe API projection | хранить bot secret/auth verdict/session/task state, route/effect, вызывать model напрямую |
| Nobus Core | identity/auth/session, route, tenant/scope, state, idempotency, approvals, effects, recovery, delivery | принимать client/model authority без повторной проверки |
| Authoritative state | единственная task/event/result/approval/effect/outbox truth | зависеть от browser memory как durable source |
| Local Codex/runtime | выполнить bounded instruction и вернуть typed events/result | credentials, policy/state transition или direct effect authority |
| Application adapters | выполнить разрешённый effect и записать receipt | расширять approved target/payload |
| Telegram/Mini App projections | показать safe status/result/artifact | раскрывать raw payload/path/secret/other-tenant data |

Mini App client и LLM/worker — недоверенные. Core остаётся единственным
orchestrator.

## 4. Mini App Web Boundary

Это один минимальный deployment unit:

- static HTML/CSS/ES modules без remote UI dependencies;
- public HTTPS ingress;
- `POST /v1/webapp/session` для bounded unchanged pass-through raw
  Telegram `initData` в Core;
- read-only task/event/result/artifact endpoints первого slice;
- позднее — natural-text task create и accept/reject immutable challenge.

Он не имеет:

- DB, queue, policy/effect engine или Agent Registry;
- arbitrary path, shell, raw prompt/log/env/config endpoints;
- Git remote, process/service or deploy control;
- provider credentials или direct effect route.

Public ingress связан с local Core одним outbound-authenticated transport.
Transport не хранит task payload. При разрыве Mini App показывает bounded
unavailable state; execution authority не переносится на edge.
Граница не имеет bot token/secret, не выдаёт auth verdict/session и
не кэширует raw `initData`, bearer или auth verdict.

## 5. Telegram authentication и browser boundary

Порядок нельзя менять. Boundary выполняет только шаг 1 и
передаёт bytes без изменения; шаги 2–9 выполняет только Core:

1. ограничить raw body/time/headers;
2. распарсить без доверия полям;
3. проверить Telegram signature для exact bot;
4. проверить `auth_date`, future skew и short TTL;
5. проверить exact owner identity;
6. поглотить replay/session generation в authoritative state;
7. выдать short-lived opaque bearer один раз и валидировать его
   при каждом API request;
8. связать session с owner/tenant/bot/origin/release generation;
9. все task/artifact refs повторно проверить server-side.

`initDataUnsafe`, client timestamp, tenant, role, risk, capability, target,
state и approval payload не являются authority.

Обязательны exact Host/Origin, same-origin API, no wildcard CORS, CSP,
`object-src 'none'`, `base-uri 'none'`, no-referrer, nosniff, no sensitive
cache, body/query/rate bounds и sanitized errors. Bearer хранится только в
memory, не URL/`localStorage`/logs.

## 6. Task и effect flow

```text
trusted ingress
  -> Core idempotency + task admission
  -> authoritative state / queue
  -> local Codex/runtime
  -> Core schema/tenant/capability validation
  -> result revision/digest
  -> runtime approval only if policy requires
  -> application effect / receipt
  -> durable outbox
  -> Telegram and Mini App projections
```

Критические инварианты:

- один ingress idempotency key создаёт не более одной authoritative task;
- owner/session-bound mutating request id проходит до Core без
  изменения и связывается с operation/request digest;
- Boundary не очередит и не повторяет mutation вслепую: после
  lost ACK выполняется Core readback/reconciliation по тому же request id;
- WorkerEvent не является state transition authority;
- provider unknown блокирует blind retry;
- delivery unknown допускает только повтор delivery;
- approval resolve выполняется по immutable server challenge, не по client
  action details;
- artifact download owner/tenant/task/revision-bound;
- restart сохраняет task/job/effect/approval authority и fence stale lease.

## 7. Tenant, data и secrets

- tenant/owner/task входят во все authority lookups;
- cross-tenant refs fail closed;
- exact local paths остаются внутри trusted local adapter;
- secret, token, cookie, credential, raw audio/payload, argv/env и raw
  stdout/stderr не попадают в client/log/evidence;
- model input — bounded untrusted data без credentials/effect tools;
- exception и owner-visible event используют allowlisted safe fields.

## 8. Gate 1 WIP reuse boundary

Переиспользуются trusted ingress, voice boundary, strict model proposal without
authority, deterministic re-derivation, durable queue/state/outbox,
idempotency/effect reconciliation и negative tenant/effect tests.

Не переиспользуется автоматически весь dirty worktree. Он остаётся frozen
`HOLD / NOT_ACCEPTED`; любой будущий reuse — отдельный exact diff из recovery
source. Широкий IntentEnvelope migration, provider qualification и Gate
ceremony не блокируют Mini App slices.

## 9. Process roles не runtime roles

Архитектор, диспетчер, исполнитель, L2 reviewer и L3 reviewer — роли процесса
Codex. Они не создают новые runtime `AgentRole`, API или services.

Архитектор включается только при изменении contract/schema/trust/authority/
storage/migration/deployment/irreversible effect. В обычном slice диспетчер
после task contract передаёт непересекающуюся file zone исполнителю.

Development lifecycle:

`TASK -> WIP_ITERATION -> CHECKPOINT -> GATE_CANDIDATE -> MERGE -> RELEASE_PRODUCTION`.

Target L1 выполняется во время WIP. Независимый L2/L3 — по frozen candidate.
Product/runtime approvals из docs 06/07 остаются отдельной властью над
пользовательскими effects.

## 10. Recovery и rollout

- новый web boundary можно отключить без изменения Telegram/Core state;
- code rollback отделён от authoritative data restore;
- до restore фиксируется watermark и reconciles unknown effects;
- DB restore нельзя применять, если потеряются более новые authoritative
  task/effect facts;
- Gate 1 worktrees/refs/bundles/stash сохраняются;
- full Gate 2A возвращается в рассмотрение только новым ADR по измеримому
  trigger.

## 11. Проверяемая интеграция slice

Slice интегрирован, когда:

1. имеет один business outcome и 3–7 acceptance criteria;
2. trust/data/effect boundary описана;
3. happy path и negative auth/tenant/replay/failure cases автоматизированы;
4. changed bytes связаны с exact Git revision/digest;
5. WIP target L1 проходит;
6. frozen candidate получил independent L2 и adversarial L3;
7. CURRENT сообщает только воспроизводимые факты.
