# Исправления классификации первоначальной проверки L3

Это отдельное дополнение к `CODE-REVIEW-08cfff0.md` и `CODE-RECEIPT-08cfff0.json`. Первоначальные отчёты, FAIL, XML и логи не переписывались. Их утверждения следует читать с поправками ниже.

1. **Первоначальный startup probe — VERIFIER_DEFECT.** `ResilientCodexAdapter(primary, None, None)` завершается `worker_configuration_invalid` в конструкторе до `control.start()`. Поэтому `startup.log` не доказывает недоступность generation после запуска. Первоначальный отчёт ошибочно приписал этому FAIL другую точку отказа. Исправленный отдельный `adversarial_recheck_probes.py` задаёт валидные fallback.execute/verifier.verify. Повтор на точном `08cfff031803211334f6da9da377b18226c5a393` воспроизвёл `durable Telegram worker unavailable` уже после start; это новое самостоятельное доказательство C3-L3-03, сохранённое в `corrected-old.log/xml`.

2. **Clock.advance probe — VERIFIER_DEFECT / неподтверждённая предпосылка.** Передача искусственного clock без подключения его к store не доказывает фактическое истечение lease внутри SQLite lock. Первоначальный `test_part_receipt_rechecks_clock_after_store_lock` нельзя использовать как доказательство C3-L3-04; он сохранён и исключён из новых приёмочных запусков. Авторитетное воспроизведение использует реальный SQLite write lock и реальное время. Копия L2 `actual_lock_probes.py` на старом `08cfff` дала 3 FAIL (part receipt, whole receipt, manifest); на `fd5f9ce` и `e6190be` эти проверки прошли. Проверка ожидания Core lock с истечением queue lease также прошла на исправлении.

3. **Stale effect probe уточнён без ослабления ожидания.** Отдельная повторная версия содержит точный capability_token в payload effect job. Это отделяет stale lease от отказа по отсутствующей привязке токена. На старом `08cfff` NETWORK stub всё равно исполнялся один раз; на исправлениях `fd5f9ce` и `e6190be` остановлен до вызова stub. Исходный probe сохранён.

4. **14 regression FAIL первоначальной ревизии остаются VERIFIER_DEFECT.** Legacy fixtures создавали control через object.__new__ без `_cleanup_pending`; production constructor поле задавал. После исправления fixtures содержательные проверки прошли: `fd5-regression.xml`, 341 PASS. Это не 14 найденных product failures.

5. **Проверка product source hashes учитывает смешанные окончания строк.** Начальная попытка сравнить smoke raw SHA256 с LF detached checkout, затем с uniform CRLF, была неверной предпосылкой verifier. Изменённые через patch файлы могли иметь смешанные окончания. Итоговая проверка самостоятельно сверила 95 неизменённых raw файлов и их LF-нормализованные bytes с точными Git objects fd5. Для двух уже изменённых startup файлов используется явно указанное contemporaneous L2 readback 97/97 до правок; старые raw bytes отдельно не сохранялись. Hash квитанции L2: `3b6d1f74bb36786c665916f6f75a5fa31cc8ff6d295de8c9221d08e20dfd1451`. Это атрибуция чужого независимого наблюдения, а не заявка на повторное собственное чтение утраченных raw bytes.

Первоначальный CODE REJECT на `08cfff` сохраняется по подтверждённым C3-L3-01/02 и отдельно воспроизведённым 03/04. `fd5f9ce` закрывает эти дефекты, но получает новый C3-L3-05 по незавершённому startup после close и отсутствию deadline. Старый C3-L3-05 воспроизводится двумя отдельными FAIL; исправление проверено на `e6190be`.
