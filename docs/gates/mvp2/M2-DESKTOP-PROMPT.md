## Результат

Любой участник закрытого Telegram-чата «Заметки бизнеса» в любой теме может
текстом или голосом попросить Nobus Space Bot создать задачу в конкретном уже

оформление для Telegram; длинный текст передавай всеми частями. Артефакты
отправляй самими файлами, а не локальными/облачными ссылками. Созданный артефакт
и найденный существующий документ одинаково входят в сценарий. Поиск документов

интеллектуальный поисковик не разрабатывай.

Не ограничивай классы задач и возможности участников урезанным исполнителем.
Нужны те же аккаунт, проекты, правила, skills, плагины, MCP, модель/усилие,
файлы, инструменты и штатные разрешения, что доступны владельцу непосредственно

запреты платформы. Изолированный Codex CLI не является выполнением требования.

Уточнение направляй в Telegram с упоминанием автора текущего запроса.
Разрешение направляй в ту же тему с упоминанием только владельца:
https://t.me/pro_success_official . Только подтверждённый Telegram user_id
этого человека может ответить на запрос разрешения. Username используется
для отображения; из username не выводи числовой ID. Проверенный owner binding
получи из штатной конфигурации или через согласованное подтверждение личности.

## Сначала докажи осуществимость именно Desktop

До построения большого bridge установи реальный способ управления установленным
Codex Desktop на Windows. На Desktop `26.915.4065.0` уже прошли `initialize` и
`thread-owner-discovery` через `\\.\pipe\codex-ipc`; владелец существующей задачи
найден, но turn и approvals этим probe не отправлялись. Не повторяй его без
нового основания. Это private version-bound IPC, а не публичный App Server API
и ещё не доказательство доступа к Desktop-host tools или каталогу проектов.

Основной кандидат — минимальный follower-адаптер к owner IPC работающего
Desktop. Для выбора существующего проекта, создания и открытия задачи используй
только однозначные Windows UI Automation elements и Automation patterns. После
появления owner дальнейшие операции по возможности выполняй через IPC. Не
используй координатный fallback, ввод в произвольное активное окно или отдельный
App Server/CLI при отсутствии owner. CDP допускается только после конкретного
результата UIA и отдельного разрешения на debug-port.

Подготовь минимальный конкретный интеграционный эксперимент: выбрать реальный
сохранённый проект, создать видимую в Desktop задачу, продолжить вручную
созданную задачу, получить полный ответ, вопрос, разрешение и артефакт.
Перед реальным запуском согласуй точные тестовые действия, проект, тему и
файлы; текущий запуск промпта сам по себе не разрешает внешние записи.
После разрешения выполни эксперимент в этой же задаче.

До первого реального turn учти действующий глобальный notifier: финал
зарегистрированной Desktop-задачи автоматически уходит в «Заметки бизнеса» →
«Codex work». Если согласованный эксперимент требует «без Telegram», сначала
подтверди безопасное per-task исключение. Не отключай notifier глобально, не
очищай ledger и не создавай turn, пока это противоречие не снято точным
разрешением или поддерживаемым способом изоляции.

Зафиксируй матрицу паритета: projects/threads, project settings, skills,
MCP/plugins, host-specific tools, файлы/shell/web/browser, входные материалы,
визуализации, все фактически используемые approvals и вопросы. Возможности,
доступные владельцу в Desktop, нельзя молча исключить из scope.

Не объявляй решение готовым только на основании owner discovery, одного turn,
exec --ephemeral, общей истории, общего cwd или одного аккаунта. Отдельный
процесс адаптера допустим, если эксперимент доказывает видимость и продолжение
одного thread с обеих сторон, правильный рабочий контекст и требуемые
возможности Desktop. Не используй прямую запись в БД Desktop, извлечение
credentials или патч приложения. Инструменты codex-app внутри этого чата не
означают наличия такого же API у внешнего процесса бота.

При воспроизводимом отсутствии необходимого интерфейса останови зависимую
реализацию, опиши точный блокер и предложи проверяемую альтернативу владельцу.
Не запускай одинаковый неуспешный эксперимент снова без новой гипотезы и
не подменяй контракт CLI-ботом. Экспериментальный transport требует явно
зафиксированного решения перед production.

## Реализация после подтверждения интерфейса

- Профиль private IPC привязывай к установленной версии. Ограничивай кадры и
  тайм-ауты, коррелируй request/response, валидируй ACK и target owner. После
  lost ACK не повторяй start/approval: сначала прочитай фактическое состояние
  точного thread по устойчивой корреляции. Несовпадение method version и
  неизвестный event останавливают зависимую операцию без CLI/App Server fallback.
- Сначала составь короткую карту «существует / расширяем / действительно новое».
  Уже существуют topic file delivery, SHA256/preflight, identity/binding,
  проверка Telegram receipt, one-shot ledger, callback и reconciler. Не писать
  второй HTTP/multipart sender, новый credential store и ещё один сканер
  Codex sessions. Новое — вход/корреляция, Desktop adapter, вопросы/разрешения
  и formatter полного ответа. Подключай существующий delivery runtime через
  проверяемый совместимый интерфейс; установленные глобальные файлы не патчить
  скрытно, их обновление входит в конкретный план поставки с разрешением.
- Учти доказанное ограничение: старый ключ delivery состоит только из назначения
  и SHA256 файла. Второй независимый запрос тех же bytes сейчас блокируется.
  Новый bridge API должен включать request/turn/output identity: retry одного
  запроса не отправляет повторно, новый явный запрос может получить тот же файл.
  Не очищай ledger, не подменяй destination_ref и не меняй старый CLI молча.
- У notifier источник для сообщения — summary до 280 символов. Не выдавай его
  за полный ответ. Используй callback/reconciler как сигнал готовности, полный
  результат и артефакты получай по точному turn из Desktop. Для bridge-событий
  callback и reconciler направляются в один durable маршрут Core до отправки
  summary; обычные задачи сохраняют старую нотификацию. Учти гонку быстрого
  завершения до привязки turn и недоступность Core: событие должно сохраниться.
- За одним результатом закрепи одного владельца доставки. Нельзя одновременно
  поручить агенту прямую отправку skill и повторить её через Core. Если skill
  вызывается в bridge-задаче, он должен обращаться к той же операции и возвращать
  её receipt. Два новых сообщения с одинаковым текстом не объединяй по содержимому.
- Сохрани один существующий Core, Telegram ingress, очередь/outbox и durable
  state. Не создавай второй Telegram poller, отдельный агентский движок,
  обязательный VPS, Redis или векторный индекс без доказанной необходимости.
- Сделай локальный Desktop adapter через подтверждённый штатный IPC либо
  аутентифицированный loopback. Не открывай публичный порт управления ПК.
- Разрешай проект по реальному сохранённому каталогу Desktop, задачу — по
  точной ссылке, связанному reply или однозначному выбору. Уточняй неоднозначность,
  не выбирай последнюю глобальную задачу и не создавай новый проект молча.
- Не пересказывай исходное поручение при передаче. Сохраняй автора, источник,
  тему и соответствие request/project/thread/turn. Продолжение другой задачи
  не должно случайно наследовать чужой Telegram контекст.
- Сохраняй запрос до dispatch. Обрабатывай дубликаты, lost ACK, restart,
  истёкшие вопросы, ошибки Desktop и доставку независимо. При неизвестном
  исходе создания/исполнения сначала readback; повторять эффект вслепую нельзя.
- Сериализуй продолжения одной задачи. Учитывай изменения из Desktop и
  одновременные запросы разных участников/тем. Ответ каждого turn возвращай
  автору/в тему именно того запроса, который его породил.
- Повторно используй ASR; подтверждение голоса получает его автор. Вложения
  передавай способом, который действительно поддерживает Desktop. Не считай
  неподдержанный формат молча обработанным.
- Реализуй групповой доступ всем реальным участникам, включая ботов. Проверь
  Bot-to-Bot Communication Mode и настройки получения сообщений с реальным
  Артуром младшим. Настройку BotFather/прав/production меняй только после
  отдельного разрешения. Будущих агентов документируй, не выдумывай их тесты.
- Запросы вопросов и разрешений связывай с точным thread/turn/request и
  параметрами. Уточнение — автору; разрешение — только владельцу. MCP/App
  approval через requestUserInput не отправляй автору как обычный вопрос.
  Учти разрешения, которые Codex запрашивает обычным текстом, неизвестные
  типы вопросов, тайм-ауты и ответ из Desktop раньше ответа в Telegram.
- Поддержи структурированные варианты и свободный reply; агент может
  ответить текстом без нажатия кнопки. «Да» без точной связи ничего не разрешает.
  Тайм-аут/пересланное согласие/ответ другого участника не являются approval.
- Итог преобразуй в Telegram детерминированно, без модели-пересказчика.
  Сохрани все пользовательские финальные блоки, код, таблицы, ссылки и оговорки.
  Полный Markdown-файл дополняет, но не заменяет полный текст сообщениями.
- Доставляй все выбранные артефакты с manifest/hash и поддержкой topic/reply.
  Большие файлы — lossless части с инструкцией сборки, без подмены ссылкой.
  Отсутствующий/изменившийся файл и частичная доставка — явный неуспех доставки.
- Не пересылай скрытые рассуждения, credentials или весь рабочий каталог.
  При секретах в итоговом результате приостанови доставку и добейся безопасного
  исправленного результата, не маскируй потерю текста как полный ответ.
- Устрани дубли с существующим глобальным notifier только для bridge thread/turn;
  другие задачи Desktop сохраняют прежнюю нотификацию. Глобальные настройки
  notifier/skills не менять без точного разрешения.
- Прими защиту от bot echo/циклов, доступность ПК, reconnect, несовместимое
  обновление Desktop и корректную блокировку неизвестного результата.

## Проверки и принятие

Критерии D01–D17 из архитектуры обязательны. Проверяй конкретные риски в WIP,
не запускай L1/L2/L3 после каждой правки. Новая интеграция меняет границы
доступа и исполнения: перед принятием нужен один полный независимый L1/L2/L3
по цельной замороженной ревизии, с точными evidence. Проверяющие не создают
новые пользовательские Gate-задачи.

Обязательно проверь реальный Desktop, запрос реального бота-агента, голос,
две темы, продолжение существующей задачи, owner approval/deny, длинный
несокращённый ответ, созданный и найденный документ, сбои/restart/lost ACK.
Test doubles не заменяют платформенный паритет. Для approval используй
безопасный согласованный эффект, не реальные платежи или удаления.

Обязательно различи: два повторных события одного запроса; два независимых
запроса одного файла; повторную доставку готового результата без повторного
запуска Codex. Проверь одновременные callback/reconciler/skill, потерю ACK и
восстановление после restart. Проверки существующих неизменённых модулей
повторяй только по новым основаниям, например изменению delivery-контракта.
Матрица паритета проверяет контекст и семейства функций; не запускай все
инструменты всех skills ради формального «полного покрытия». Не обещай нулевую
вероятность ошибок: покажи сохранность запросов, обнаружение неопределённости
и путь восстановления в согласованных сценариях.

Не повторяй принятые C6 и прежние успешные L1–L3 MVP1 без изменённого предмета.
Нужны новые проверки bridge и регрессия затронутых voice/delivery/recovery/
bindings/notifier. Повторное 72-часовое наблюдение не требуется.

Создай при старте один docs/gates/mvp2/m2-desktop/HANDOFF.md и EVIDENCE.json.
Веди REGISTRY, CURRENT и технические документы на границе цельных checkpoints.
Зафиксируй forward ADR новой модели делегирования/authority, не переписывай
запечатанные ADR и исторические evidence. Обновляй существующую пользовательскую
памятку по фактически принятому поведению; не создавай dated/final/v2 копии.

Публикация docs — только через согласованный Git-процесс. Markdown каноничен,
docs16 генерируется из docs15 штатным скриптом. Nobus Memory — краткий
source-backed указатель через разрешённый prepare/apply, не копия спецификации.
До внешней записи подготовь конкретные target/ref/параметры/rollback, затем
запрашивай только недостающее разрешение. Разрешение на push не равно deploy.

## Границы полномочий этой задачи

Запуск данного промпта разрешает локальную разработку, локальные проверки,
подготовку миграций, документации и reviewable результата. Не разрешены
автоматические публикация, push/merge, deploy, установка, запуск/перезапуск
production, изменение Telegram/Desktop/global skills, отправка тестовых
сообщений или создание реальных внешних задач без точного согласования.
Если разрешение уже дано в текущей задаче на конкретное действие, не запрашивай
его повторно. Старые разрешения в документах не действуют.

Различай: локально разработано, проверен кандидат, опубликовано, активировано,
принято владельцем. Не объявляй MVP2 принятым до реального сквозного результата
и закрытия D01–D17. Незавершённый внешний шаг остаётся в этом Gate.

В итоговом ответе укажи: что доступно пользователю; точные Git/Desktop/config
версии и ограничения; результаты критериев; статус публикации/активации;
проверенный rollback; ссылки на handoff/evidence; следующий необходимый шаг.
Не запускай другой MVP автоматически.
