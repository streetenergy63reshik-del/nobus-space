## 2. Определение готового MVP-1

MVP-1 — owner-bound Telegram-оркестратор, который принимает обычные текстовые
и голосовые задачи, понимает бизнес-намерение без обязательных slash-команд,
безопасно работает с Google Workspace и документами владельца на ПК, выполняет
проверяемый анализ и возвращает либо сохраняет результат в нужном формате.

MVP-1 принят, когда владелец одним естественным запросом может:

1. получить резюме «Заметок бизнеса»;
2. прочитать, создать или изменить Calendar event;
3. прочитать, создать, изменить или завершить Google Task;
4. найти документы на Google Drive и в `C:\Хранилище\АГЕНТ`;
5. проанализировать один или несколько Google/local документов;
6. отфильтровать данные по клиенту, артикулу, периоду и другим сущностям;
7. получить воспроизводимые расчёты и явно указанные источники;
8. получить Telegram text, JPEG либо self-contained HTML;
9. создать XLSX, DOCX, PDF, Google Docs или Google Sheets;
10. сохранить новый результат локально и/или на Google Drive;
11. контролируемо обновить существующий локальный или Google-документ;
12. получить понятную безопасную ошибку, а не общий необъяснимый отказ.

## 3. Неподвижные продуктовые принципы

### 3.1. Natural Language First

- основной интерфейс — обычный текст и голос;
- slash-команды — только операционный fallback;
- точная «магическая» формулировка не требуется;
- неоднозначность ведёт к одному понятному уточнению;
- кнопки допустимы для подтверждения/выбора, но не обязательны для начала
  продуктовой функции.

### 3.2. Codex управляет, Google усиливает

- Codex остаётся основным reasoning/control brain;
- Gemini применяется как Google-specialist для подходящего анализа и research;
- Nobus Core, а не модель, управляет правами, риском, idempotency и состоянием;
- модели не владеют OAuth, shell или ambient filesystem authority;
- внешние эффекты выполняют application-owned adapters.

### 3.3. Google и ПК равноправны

Google Drive/Docs/Sheets и `C:\Хранилище\АГЕНТ` поддерживают одинаковый
продуктовый lifecycle:

`search → select → read → analyze → create → update → deliver`.

### 3.4. Безопасность не должна разрушать продукт

Проверки выполняются на доверенных границах и не превращаются в четыре
пользовательских клика. Точная owner-команда разрешает указанное обратимое
действие в заранее разрешённом scope. Необратимые и высокорисковые действия
сохраняют отдельный L4.

### 3.5. CURRENT отдельно от TARGET

Документ или ADR не доказывает работающий runtime. Готовность подтверждают
только точный commit, воспроизводимые тесты, L1/L2/L3, live evidence и
применимый L4.

## 4. Объём MVP-1

### Входит

- Telegram owner binding и один polling runner;
- durable queue, outbox, progress и restart recovery;
- локальная русская voice transcription;
- Natural Intent Kernel и scoped conversation context;
- Business Notes summary и task candidates;
- Calendar list/create/update;
- Tasks list/create/update/complete;
- public web research с evidence;
- Google Drive/Docs/Sheets read;
- owner library read под `C:\Хранилище\АГЕНТ`;
- Windows Local Library Bridge для server runtime;
- single- и multi-document analytics;
- cross-source Google + local analytics;
- Telegram text/JPEG/HTML;
- XLSX/DOCX/PDF artifacts;
- Google Docs/Sheets create;
- Drive upload нового разрешённого артефакта;
- snapshot/revision-bound update;
- L1/L2/L3, audit, backup, rollback и 72-часовой pilot.

### Не входит

- удаление реальных документов без отдельного L4;
- произвольное изменение sharing/access;
- отправка клиенту или третьей стороне без отдельного L4;
- деньги, покупки и платежи;
- массовые фоновые незапрошенные операции;
- arbitrary shell или прямой filesystem tool модели;
- чтение `C:\Хранилище\АГЕНТ\VPN данные`;
- коммерческий multi-tenant SaaS;
- автономное самоизменение политик, skills или prompts.

## 5. Целевая архитектура

```text
Telegram text/voice
  -> Trusted Telegram Ingress
  -> local voice transcription (если voice)
  -> IntentEnvelope
  -> Nobus Core / Policy / Durable Queue
       -> Business Notes adapter
       -> Calendar / Tasks executors
       -> Google Document Gateway
       -> Windows Local Library Bridge
       -> Codex primary worker
       -> Gemini specialist gateway
  -> normalized facts / proposed effect
  -> L1 / L2 / L3
  -> ResultComposer / Effect Executor
       -> Telegram text/JPEG/HTML
       -> local artifact
       -> Google Docs/Sheets/Drive
```

### 5.1. Server Nobus Core

Владеет:

- Telegram polling;
- durable queue/outbox;
- task/effect state;
- policy и audit;
- Codex/Gemini gateways;
- Google Workspace adapters;
- verification orchestration;
- ResultComposer.

Server не получает SMB/share или произвольный filesystem-доступ к Windows-ПК.

### 5.2. Windows Local Library Bridge

Bridge:

- работает под отдельной минимальной identity;
- не является Telegram runner;
- не хранит Telegram или Google credentials;
- связывается с Core через device-bound mutual authentication;
- принимает только подписанный закрытый job;
- не публикует shell, PowerShell или arbitrary path API;
- проверяет root identity и containment перед каждой операцией;
- возвращает content/revision только в пределах job contract.

Когда Bridge offline, Google/Telegram продолжают работать. Локальная задача
становится `DEGRADED` либо безопасно ожидает reconnect; write не повторяется
вслепую.

## 6. Единые контракты

### IntentEnvelope

```yaml
schema: nobus.intent.v1
tenant_id: trusted value
conversation_ref: tenant/chat/topic binding
modality: text | voice
owner_text: bounded normalized text
domain: notes | calendar | tasks | documents | research | general
action: closed action enum
entities: closed bounded object
period: explicit normalized range | null
source_scope: bounded references
requested_outputs: [telegram_text | jpeg | html | xlsx | docx | pdf | google_doc | google_sheet]
proposed_effects: [closed effect kind]
confidence: decimal
ambiguities: [string]
```

### DocumentRef

```yaml
schema: nobus.document_ref.v1
backend: local | google
tenant_id: trusted value
project_ref: string
client_ref: string | null
source_id: opaque relative-path handle | google file id
revision: sha256 digest | google revision
media_type: string
classification: public | internal | confidential | restricted
provenance: bounded object
```

### DocumentQuery

Описывает source, project/client, file/folder hints, period, media types и
maximum candidates. Поиск metadata-first; содержимое не читается до selection.

### DocumentReadPlan

Описывает exact `DocumentRef`, ranges/pages/sheets, byte/character limits и
purpose. Перед чтением revision/digest перепроверяется.

### AnalysisRequest

```yaml
client: string | null
sku_or_article: string | null
period: normalized range | null
sources: [DocumentRef]
metrics: [closed metric request]
grouping: [string]
calculation_rules: [versioned rule]
requested_outputs: [closed output]
limitations: [string]
```

### ArtifactPlan

Описывает title, format, content sections, normalized tables/charts,
provenance, target backend и destination hint.

### DocumentWritePlan

```yaml
backend: local | google
operation: create | update
target: exact output root/path or google folder/file id
expected_revision: digest/revision | null
artifact_digest: sha256
collision_policy: new_version | ask
snapshot_required: boolean
idempotency_key: string
approval_binding: exact owner request or preview confirmation
```

Неизвестные поля и enum запрещены. Durable state не хранит открытый текст
локального документа без отдельного зашифрованного контракта.

## 7. Owner library `C:\Хранилище\АГЕНТ`

### 7.1. Source scope

Owner root один: `C:\Хранилище\АГЕНТ`.

Фактические project/client roots задаёт versioned source registry. Модель не
получает абсолютный owner root. Metadata index ограничен по количеству entries,
кандидатов и времени.

### 7.2. Always-deny

- `C:\Хранилище\АГЕНТ\VPN данные`;
- произвольное чтение `C:\Хранилище\АГЕНТ\Системные`;
- `Nobus memory backups`;
- `.git`, `.runtime`, `.venv`, caches, logs и temp;
- secret/token/credential-like names;
- symlink, junction и другие reparse points.

`Nobus memory` обслуживается только curated memory adapter.

### 7.3. Output scope

Локальная запись разрешена только в versioned output registry. Destination
выводится из project/client binding, а не придумывается моделью.

Новый путь создаётся без второй кнопки, если точная owner-команда содержит
неизменившиеся format/destination. Collision не перезаписывает оригинал:
создаётся новая версия либо запрашивается выбор.

Update требует snapshot, digest CAS, diff preview, atomic replace и readback.
Удаление не входит в обычный контур.

## 8. Google Workspace

### 8.1. Read plane

- Calendar/Tasks/Drive/Docs/Sheets читаются через официальные API;
- Drive search metadata-first;
- Google Docs читается структурированно либо через проверенный export;
- Google Sheets читается ranges, а не полным blind export;
- API/MCP transport failure не интерпретируется как отсутствие данных.

### 8.2. Intelligence plane

- Codex — основной planner/analyst;
- Gemini — специализированный Google worker;
- Preview Google agents только за feature flag;
- provider outage не блокирует Telegram polling;
- read-only fallback bounded;
- costs и retention контролируются Core.

### 8.3. Write plane

Поддерживаются:

- Calendar create/update;
- Tasks create/update/complete;
- Google Docs create;
- Google Sheets create;
- Drive upload нового HTML/JPEG/XLSX/DOCX/PDF;
- revision-bound update существующего Docs/Sheets.

Если exact payload/target изменился после исходного owner request, Core обязан
показать preview и получить естественное подтверждение. Unknown write outcome
сначала проходит reconciliation; blind retry запрещён.

Sharing/access changes и delete требуют отдельного L4.

## 9. Документная аналитика

### 9.1. Query planning

До чтения формируется точный plan: client, SKU/article, period, sources,
metrics, grouping и output. Огромный файл не передаётся модели целиком.

### 9.2. Extraction

Предпочтение:

1. structured values/ranges;
2. локальное детерминированное извлечение;
3. bounded excerpts;
4. OCR только для scanned PDF и только после отдельного corpus gate.

### 9.3. Calculations

Формулы выполняются отдельно от narrative. L1 проверяет типы, диапазоны,
тоталы и invariants. L2 независимо пересчитывает. L3 ищет ложную причинность,
scope leak и подмену отсутствующих данных.

### 9.4. Conflict handling

Расхождение источников не разрешается молча. Результат показывает:

- какие значения расходятся;
- из каких files/sheets/pages они получены;
- какая revision использована;
- что требуется от владельца.

### 9.5. Result formats

Короткий вопрос получает Telegram text. Сложный результат может вернуть JPEG и
self-contained HTML. Один HTML source используется также для JPEG screenshot и
PDF render; XLSX/DOCX строятся из тех же normalized facts.

## 11. Отказы и поведение

| Отказ | Поведение |
|---|---|
| Intent ambiguous | Уточнить, не исполнять |
| Google provider unavailable | Bounded read fallback или безопасный failure |
| Google write outcome unknown | Reconciliation до любого retry |
| Bridge offline | Local DEGRADED; Google/Telegram продолжают работу |
| Local file revision changed | Conflict; не перезаписывать |
| Google revision changed | Conflict; новый preview |
| Secret/DLP boundary | Fail closed, без model transfer |
| Prompt injection в документе | Данные без tools/authority |
| Duplicate Telegram/update/job | Idempotent replay |
| Orphan PENDING | Reconcile; composite health не PASS |
| Второй Telegram runner | Publication blocked |
| Technical release failure | Stop + verified rollback; no automatic retry |
| Процедурная ошибка smoke | Исправить на том же runner без rollback |
| Неоднозначная ошибка | Остановиться и запросить владельца |

## 12. Дорожная карта

Все Gate выполняются последовательно. Следующий Gate не начинается, пока
интеграционная задача не приняла handoff предыдущего.

### Gate 0 — Product Contract и baseline

**Цель:** фактический read-only baseline, CURRENT/TARGET, contract и test corpus.

**PASS:** exact base commit, runtime evidence, registries/deny design, минимум
80 natural requests, Gate handoff.

**L4-сообщение:**

```text
Разрешаю Gate 0 MVP-1 Nobus Space.

Разрешаю read-only проверку runtime, процессов, Windows Scheduler, server
configuration metadata, репозитория, релевантных ADR/handoff/Nobus Memory и
metadata-only верхнего уровня C:\Хранилище\АГЕНТ. Разрешаю изменить только
локальную документацию и тестовый корпус, провести L1/L2/L3 и создать один
локальный commit Gate 0.

Запрещаю чтение C:\Хранилище\АГЕНТ\VPN данные и произвольное чтение
C:\Хранилище\АГЕНТ\Системные, изменение live runtime, Google/Telegram writes,
изменение owner files, deployment, remote и push. Существующие изменения
сохранить и не включать без доказанной принадлежности Gate.

При неоднозначности остановиться и запросить решение владельца.
```

### Gate 1 — Natural Language и Voice Kernel

**Цель:** единый IntentEnvelope и разговорный интерфейс.

**PASS:** golden text/voice corpus, scoped follow-up, safe clarification,

## 13. Gate handoff contract

Каждая отдельная задача Gate обязана вернуть:

- Gate number/name;
- exact base commit;
- exact result commit;
- manifest изменённых файлов;
- CURRENT before/after;
- TARGET remaining;
- deterministic L1 evidence;
- independent L2 evidence;
- adversarial L3 evidence;
- применённый L4 и receipts;
- backups/migrations/external effects;
- open risks;
- `READY` либо `BLOCKED`;
- точные входы для следующего Gate.

Rework аннулирует evidence предыдущей revision. Следующий Gate не принимает
устное «готово» без handoff.

## 15. Definition of Done

MVP-1 не считается готовым, пока:

- Gate 0–8 не имеют accepted handoff;
- exact release commit не зафиксирован;
- L1/L2/L3 не PASS;
- server/Bridge/Google/runtime composite health не PASS;
- polling readiness не свежий;
- orphan PENDING или неизвестный write outcome не reconciled;
- хотя бы один обязательный natural smoke не пройден;
- backup/rollback не проверены;
- 72-часовой pilot не завершён;
- TARGET ошибочно описывается как CURRENT.

## 16. Change control

Изменение принципов Natural Language First, Google/local parity, trust
boundaries, матрицы полномочий, Gate sequence либо Definition of Done требует:

1. impact analysis;
2. изменения или нового ADR;
3. обновления этого документа;
4. проверки ссылок/терминов/контрактов;
5. независимых L2/L3;
6. явного одобрения владельца, если меняются права, внешние действия, стоимость,
   удаление или production behavior.

Один баг или успешный кейс не меняет этот эталон автоматически.
