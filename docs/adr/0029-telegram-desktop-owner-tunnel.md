# ADR 0029 — Telegram-туннель к владельцу задачи Codex Desktop

**Статус:** ACCEPTED FOR M2-DESKTOP IMPLEMENTATION  
**Дата:** 22 сентября 2026 года

## Контекст

MVP2 должен управлять задачами уже установленного Codex Desktop из закрытой
группы «Заметки бизнеса». Отдельный CLI или App Server может читать общую
историю, но не сохраняет владельца активной Desktop-задачи и не доказывает
паритет её инструментов и разрешений. На Desktop `26.915.4065.0` проверен
локальный owner/follower IPC через `\\.\pipe\codex-ipc`; Windows UI Automation
даёт однозначный bootstrap проекта и новой задачи без координатных кликов.

Группа должна принимать явные обращения от всех фактических участников,
включая ботов, но право на разрешения остаётся только у владельца. Глобальный
notifier обязан продолжать обслуживать обычные задачи и не дублировать полный
ответ bridge-задачи.

## Решение

1. M2-DESKTOP использует минимальный локальный адаптер к owner IPC работающего
   Desktop. Профиль протокола и UIA привязан к версии приложения и при
   несовместимости останавливается без fallback на CLI/App Server.
2. UIA применяется только для точного выбора сохранённого проекта и создания
   bootstrap-задачи. После обнаружения владельца turn, история, вопросы и
   разрешения идут через owner-targeted IPC.
3. Точный отрицательный `chat_id` существующего owner binding является корнем
   доверия группы. Сообщение, которое Telegram доставил из этого чата, получает
   автора `telegram:participant:<numeric user_id>` и производный auth context.
   Другой чат не принимается. Пересылка, `sender_chat`, анонимный или иной
   неидентифицируемый источник не создаёт Desktop-задачу.
4. Уточнение направляется numeric автору запроса в исходную тему. Любое
   command/file/permissions/MCP approval также показывается в исходной теме
   с numeric-упоминанием владельца; решение принимается только от его
   подтверждённого numeric user ID. Username и display name не являются
   полномочием. Прежний private-only маршрут был исправлен по A05
   независимого аудита: он не соответствовал исходному контракту владельца.
5. Один durable bridge request владеет полным текстом и файлами своего turn.
   Ключ доставки включает request, вид/номер части, назначение и digest.
   Потерянный ACK переводит операцию в неизвестный исход; повтор исполнения или
   отправки без readback запрещён.
6. Bridge до dispatch добавляет зарезервированный точный UUID-маркер
   `NOBUS-BRIDGE-REQUEST:<uuid>`. Это не смысловая эвристика: request уже
   записан в durable state, формат закрыт и проверяется notifier. Установленный
   notifier помечает такой turn `bridge_suppressed`, reconciler считает это
   терминальным исходом, а полный ответ и артефакты отправляет только bridge.
   Обычные задачи сохраняют прежний notifier.
7. Документы отправляются через установленный `telegram_delivery_runtime` и
   его one-shot ledger. Новый request получает новое request-scoped назначение,
   поэтому те же bytes можно осознанно отправить снова; replay одного request
   не создаёт второй send.

## Последствия

- Не требуется устанавливать daemon, патчить Desktop или писать в его БД.
- Доступен единый локальный процесс Telegram/Core; второй poller, sender,
  credential store и агентский движок не создаются.
- Обновление Desktop или изменение private IPC/UIA требует нового
  compatibility profile и живой проверки перед возобновлением dispatch.
- Сообщение из доверенной группы доказывает возможность автора писать в неё на
  момент отправки. После выхода участник не может создать новый запрос; уже
  принятый запрос сохраняет исходного numeric автора для аудита и reply.
- Отдельный stdio App Server остаётся допустимым read-only диагностическим
  средством, но не является транспортом продукта.

## Альтернативы

- Managed daemon отклонён как обязательный следующий шаг: проверенный способ
  запуска не имел полного локального пакета, а установленный Windows Desktop
  не выбирает этот socket как свой transport.
- Отдельный App Server отклонён как writer: после перехода задачи к Desktop он
  получил `already has an active writer`.
- Remote Connections не выбран: официальный пользовательский маршрут не
  предоставляет проверенный сторонний Telegram-client contract.
- CDP не понадобился: semantic UI Automation подтверждён и не требует запуска
  Desktop с debug-портом.

## Проверка

Решение принимается только вместе с D01–D17 M2-DESKTOP: реальный Desktop,
настоящий Артур младший, две темы, голос с подтверждением, вопросы,
approve/deny владельцем, полный длинный ответ, файлы и восстановление. Fixtures
подтверждают локальные границы, но не заменяют этот live-сценарий.
