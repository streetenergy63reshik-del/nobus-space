# C2 — срок хранения голосового ввода

Статус: продолжение C2, локальный WIP. Этот документ описывает реализованную
модель очистки; окончательная приёмка требует проверок нового кандидата.
Историческая приёмка b090bc48 остаётся BLOCKED.

Голосовой ввод хранится не дольше часа от `telegram_jobs.created_at`.
Подтверждение, повтор, продление lease и перезапуск этот срок не продлевают.
При подтверждении сырой звук уже удалён из recovery payload; после передачи
подтверждённой задачи остаётся пустая запись для защиты от повтора на 24 часа.
Созданный TaskContract и готовый результат имеют существующий жизненный цикл
задачи, а не срок хранения неподтверждённого голосового ввода.

| Место | Что хранится и когда очищается |
|---|---|
| Память загрузки | Ограниченные bytes до 10 MiB; production не создаёт файл с аудио. Ссылки освобождаются при выходе из этапа. Это не обещание немедленного обнуления каждого Python allocation. |
| Anonymous pipes | Ограниченный кадр audio/config/response; pipe handles закрываются вместе с процессом. Аудио и транскрипт не попадают в argv, stderr или служебные логи. |
| Native ASR | Один native worker в Windows Job, до 4 GiB и четырёх CPU; Windows может добавить служебный conhost, который также входит в группу очистки. Завершение при timeout до 180 секунд, отмене, shutdown или смерти родителя; после 60 секунд простоя процесс также завершается. Успех очистки требует завершённого процесса. |
| SQLite recovery | DPAPI ciphertext, исходная identity и binding. Expiry по метаданным применяется до чтения payload при startup/read/claim/maintenance, включая leased и flag-off. |
| Длительный этап | Общий deadline равен оставшемуся TTL. После download, ASR и подготовки задачи повторно проверяется срок; поздний preview или draft не публикуется. |
| SQLite/WAL | `secure_delete=ON`, очистка строк и `wal_checkpoint(TRUNCATE)`. Busy/write/cleanup failure остаётся ошибкой; следующий доступ повторяет очистку, не объявляя ложный успех. |
| Новый управляемый backup | Только quiescent voice state: просроченное содержимое очищается до проверки/copy; наличие активного непустого voice payload запрещает backup. |
| Старый backup | Исходные файлы не меняются. При restore сначала проверяется DPAPI authentication и точный hash, затем только собственная staging-копия очищается до проверки содержимого. Startup также применяет TTL. |
| Benchmark evidence | Только разрешённые синтетические записи и hypotheses в изолированном evidence. Они не являются пользовательским recovery payload; исторические frozen receipts сохраняются для воспроизводимости. В Git — код, эталоны, разрешённые индексы и агрегаты. |

DPAPI обеспечивает шифрование в контексте пользователя Windows. Здесь нет
отдельного ключа на каждую запись и нет заявления о криптографическом стирании:
сохранённая третьей стороной копия ciphertext остаётся расшифровываемой при
доступе к тому же ключу. Очистка управляемых SQLite/WAL и запрет повторного
использования просроченного содержания проверяются отдельно от этого свойства.
Физическое стирание SSD, чужих backup, системных crash dump или pagefile
не заявляется. Работающий runtime выполняет очистку при очередном доступе;
после простоя startup выполняет её до обработки. Таймер при выключенном ПК
не является гарантией продукта.

Исходное требование C2.7 и архитектурная модель допускают срок жизни
зашифрованных backup и требуют проверяемой очистки. Новая реализация закрывает
воспроизведённые дефекты доступа после TTL и копирования voice в управляемый
backup без изменения этого требования. Отдельного принятия более слабой
модели хранения здесь не заявлено.

Целевые regression cases находятся в `tests/test_voice_retention.py` и
`tests/test_voice_isolated.py`. Независимые WIP probes и прежние неуспешные
попытки сохранены в `.runtime/c2/closure/retention-probe/` и `native-review/`.
Их результаты сами по себе не заменяют итоговые L1–L3 нового C2.
